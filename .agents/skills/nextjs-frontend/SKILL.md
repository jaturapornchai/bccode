## 1. Setup & Precedence
- **Location**: `D:\bccode\frontend`.
- **References**: Always read [AGENTS.md](file:///D:/bccode/AGENTS.md) and [bc-account-core-rules.md](file:///D:/bccode/.agents/rules/bc-account-core-rules.md) first.

## 2. Dynamic Height & Scroll Locking Layout
- **Desktop Two-Pane**: 30% left pane (list/table), 70% right pane (forms/details) split.
- **Scroll Constraints**: Viewport height must be calculated dynamically in realtime using ResizeObserver. Avoid outer page vertical scrollbars. Left list and right form scroll independently with `overflow-y-auto min-h-0 h-full`.
- **Embedded WebGL Iframes**: Probe the real API readiness endpoint with a readable `response.ok` before mounting; never treat an opaque `no-cors` shell-page response as ready. Auto-retry with timer cleanup, and when a renderer can mount hidden, preserve logical node visibility until asynchronous positions exist.
- **Form Layout**: Nested checkboxes/tables inside details/forms must auto-expand vertically (no inner scrollbars). Rely on the main detail pane to scroll.
- **Inline Form Actions**: Put Save/Cancel in the fixed top header/action bar of right-side inline add/edit panes. Never require users to scroll to the bottom merely to finish or cancel an edit; bottom action areas are acceptable only when independently pinned and needed for dialog/wizard navigation.
- **Horizontal Scroll**: Avoid left-pane horizontal scroll. Apply responsive hide classes (`hidden md:inline-flex` etc.) on less important columns. Keep rows and headers aligned with flex-nowrap.

## 3. Product Category (`/productcategorygroupselectscreen`)
- **Selector Grid**: Shows 20 category-set cards (1-20). Thai UX calls each `ชุดหมวดสินค้า`, never a named category group. Keep cards equal-height and compact; preview only a few root categories plus an explicit remaining count, then show the full names inside the selected tree.
- **Toolbar**: Lift search/add/back controls into the screen header beside the title once a group is selected (no toolbar above the tree).
- **Split Pane**: From tablet width upward, keep the left tree and right detail/editor side by side around 30/70; both stretch to viewport height and scroll independently.
- **Select Before Edit**: Clicking a tree row selects it and opens MongoDB-backed read-only detail. Edit/delete live in the detail pane, add-child lives in the selected-set toolbar, and rows retain only ordering controls so narrow tree panes stay readable.
- **dnd-kit Drag-n-Drop**:
  - Pointer hold-and-drag from anywhere on the row (excluding action buttons).
  - Overlay: small transparent dashed ghost row with small left chip following pointer during drag.
  - Sibling Swap: FLIP animations for real-time order previews.
  - Drop Targets: Top 28% (insert before), middle (move inside target as child), bottom 28% (insert after), root target at bottom of tree pane (clears parent GUIDs). Reject moving parent under own child.
  - Optimistic State: Apply changes in memory immediately. Pulse dropped row and scroll to it if out of view. Refresh from API only on save error.
  - Detail action: Must use optimistic values immediately after drop.
  - Indentation: Use absolute left bars for selected indicators, do not shift text layout.
- **Editor**: Compact fields (no stretching gaps). Recursive "all child categories" list under fields.
- **Product Assignment**: `สินค้าในหมวด` uses Mongo Product master data through `/api/product` only. Key, dedupe, remove, reorder, and persisted relation all use normalized Product `code`; save only `{code,xorder,names}`. Never search ProductBarcode, display Barcode/unit columns, or persist Barcode fields in `codelist`. Every category/product counter must count the same normalized, unique, non-empty Product codes as the editor—never raw `codelist.length`, because legacy invalid rows can create phantom counts. Keep the editor mounted during record switches according to `stable-crud-editor`.

## 4. Warehouse Location Shelf (`/productwarehousescreen`)
- **UX Pattern**: Follow the Product Category workbench pattern: compact toolbar, left warehouse/location/shelf tree, right inline editor.
- **Split Pane**: Left tree and right editor must fill the available viewport height and scroll independently with `h-full min-h-0 overflow-y-auto`.
- **Density**: Keep warehouse selection, search, record count, tree rows, and editor fields compact. Do not stack a large tree card above a separate form card.
- **Languages**: Warehouse and location `names` fields must render exactly the active company languages in order; no extra fallback languages in normal forms.

## 5. Branch & Address Details (`/branch`)
- **Branch Page**: Single entrypoint for branch-scoped data. Embedded tabs: General, Address, Department, Work Day, Holiday, POS/Tax, Business Types.
- **Leaflet Map Picker**: Pick coordinates in full-screen map using OpenStreetMap (Bangkok default: 13.7563, 100.5018). Round to 6 decimals.
- **Thailand Address**: Select province -> district -> subdistrict -> zip code. Load data via `/goapi/api/address/thailand`. Recompute/clear postal code on changes.
- **Branch Settings**: Normal tables/forms (no raw JSON editors) for `paymentrounding` and `pointconfig`.
- **Thai Branch Code**: Legal head-office uses `00000`. Pad/normalize input to 5 digits (e.g. `1` -> `00001`).

## 6. UI Widgets & Interactions
- **CRUD Mutation Source**: Frontend create/edit/delete actions must call MongoDB-backed operational APIs only. Do not call PostgreSQL/ClickHouse projection or BI endpoints for mutations, and do not use derived stores as normal list/detail truth after saving. Refresh operational screens from MongoDB-backed APIs; Kafka/projection fan-out is backend-owned.
- **CRUD Right Pane Detail Source**: In left-list/right-detail CRUD screens, the right read-only detail panel and edit form must hydrate from the MongoDB-backed detail API only. List rows, PostgreSQL projections, stale caches, or fallback rows may select/highlight a record but must not be used as the right-pane source of truth. Show a clear error when detail loading fails.
- **Accounting Decimal Inputs**: Frontend accounting, finance, stock, sales, purchase, tax, payment, cost, and report screens must treat money, price, decimal quantity, exchange rate, debit, credit, and totals as decimal strings. Do not use TypeScript `number`, `parseFloat`, `Number(amount)`, unary `+amount`, or JS-number reductions for these values; use decimal-string validation and a decimal library where calculations are unavoidable.
- **CRUD Row Click**: In data-list screens, row click selects and opens read-only detail only. Edit mode must require the explicit pencil/edit button, and selected/read-only rows must not use the amber editing highlight.
- **Shared Frontend Widgets**: If a UX pattern appears in more than one menu or screen, first reuse or create a central widget/component/field renderer. Keep labels, validation, search, empty states, save/load mapping, and accessibility in that shared widget. Use page-specific UI only when the workflow is genuinely different.
- **Global Toast Notifications (set 2026-06-21)**: All notifications use the global toast — `import { toast } from "@/lib/toast"` then `toast.success/error/info/warning(text)` (or the legacy-compatible `pushNotice({ type, text })`). It renders once via `<ToastViewport/>` in `app/layout.tsx`: bottom-right, auto-dismiss 5s, stacked, themed via existing `.message`/`.success`/`.error`/`.info` classes. **Do NOT add per-screen inline notice state + banner JSX** (`const [notice,setNotice]=useState…` + `{notice ? <div className="message …"> … }`). Existing screens were migrated to `const setNotice = pushNotice`; write new code with `toast.*`.
- **Uploaded Image Format = PNG/JPG only (set 2026-06-21)**: Every image `<input type="file">` uses `accept="image/png,image/jpeg"` (a transparent-logo field may use `accept="image/png"`), plus a `file.type` guard rejecting non-PNG/JPG before upload. Client resize/crop/thumbnail encoders output PNG (PNG source → keeps transparency) or JPG — **never WebP** (`resizeImageFile`/`makeThumbnailFile`/`ImageCropDialog` in `system-settings-screen.tsx`). Thumbnails are still generated (small JPG/PNG) for list/preview speed. The backend `image_r2.go` is the authoritative guard (PNG/JPG ext + content-type) so S3 only stores PNG/JPG. Static `.webp` page-background assets are a separate concern (see Semantic Backgrounds). See core-rules "Uploaded Image Format Iron Rule".
- **Uploaded Product Video = MP4 only (set 2026-08-06)**: Product/Barcode video pickers use `accept="video/mp4,.mp4"`, allow files over 50 MB, reject non-MP4 or files over the 500 MB safety cap before upload, and stream the multipart body through a byte-counting proxy to `VideoUploadHandler`; do not parse large videos with `request.formData()` in Next.js. Before upload, capture the first displayable frame from the local file with native video+canvas, encode/upload it as JPG through the existing image path, and persist `videos[{xorder,uri,posteruri}]`. Show the authenticated still poster immediately with a play action; load the private MP4 on demand with controls/playsInline, release its blob URL after unmount, and never add video blobs to the shared image cache. Send Bearer only when the private media URL origin matches the frontend or configured backend. Keep Product-owned and Barcode-owned `videos[]` separate; Product detail may show linked Barcode videos as a separate same-company read-only group.
- **Radio/Checkbox Compact Wrap**: Follow the core rule for radio and checkbox groups: default to compact horizontal/wrapping layouts (`flex-wrap`, responsive grid, or chip/tile wrap) instead of tall one-option-per-line stacks. Keep vertical stacks only for long explanatory choices, nested/hierarchical choices, per-option help/error text, or truly narrow screens, while preserving label click targets and keyboard/focus accessibility.
- **Plain User Language**: User-facing menus, page titles, buttons, labels, helper text, empty states, validation messages, and reports must use everyday business terms that non-technical Thai SME users understand immediately. Avoid terms like schema, matrix, mapping, payload, raw JSON, GUID, collection, route, slug, and internal integration jargon in normal screens. Use terms such as `ชุดตัวเลือกสินค้า`, `เชื่อม Shopee`, and `จัดหมวดสินค้า` instead of technical labels.
- **No Raw JSON User Input**: Never render JSON-backed business setup fields as raw textarea editors for normal users. Build structured editors instead: repeatable rows, compact tables, chips, nested attribute/value editors, pickers, and import mappers. Keep raw JSON textareas only for explicit technical/admin/debug/importer screens.
- **No Ellipsis For Context Names**: Show user-facing context and identity values in full. Holding/company/branch labels, selected workspace context, users, important business codes, document numbers, report headers, and badges must wrap with `break-words`/`whitespace-normal` instead of `truncate`, `line-clamp`, fixed-height badges, or CSS ellipsis. Compact tables can stay dense only if the full value is also visible in detail/expanded content.
- **Holding Access Scope UI**: User, screen permission, permission group, user permission assignment, and approval screens are Holding-level screens. Show the active Holding in the header, then use the shared Holding scope widget for applicability: a whole-Holding checkbox, searchable company add-to-list, selected-company branch panel, branch search add-to-list, and per-company `allbranches` checkbox. The widget stores `scopetype`, `businesscode`, `branchcode`, and `allbranches`. Do not render full company/branch checkbox trees and do not expose raw JSON scope editing to normal users.
- **User Access Audit Report**: The access setup flow includes a read-only user access audit report after permissions/approvals. It must derive from existing MongoDB-backed system-setting APIs (`user`, `permissionlink`, `permissiondefinition`, `permissiongroup`, `approvalsetting`) and workspace Holding data, summarize what each user can access and do, and use a full-width report preview (`width: 100%`, no narrow preview max-width). Report effective access, not raw stored scope rows: `holding` collapses all narrower rows, and `company/allbranches` collapses branch rows for that company while preserved branch rows remain only for future toggle-off state. Do not show a persistent `Create PDF` button on the report preview; add PDF export only through a separate explicit report action if requested. Do not make it a separate editable CRUD workflow.
- **Active Company Context**: Company-owned CRUD screens require the workspace-selected company and send normalized `businesscode` through the standard API context header/claim. Backend validates company membership/scope; request bodies are never authoritative. Missing company context is a visible blocking error. Holding-wide screens are explicitly read-only aggregation and retain `businesscode` in rows/filters.
- **Quick Barcode Retail UX**: Barcode lists must honor backend `limit + offset + total` with visible paging/load-more so no SKU becomes unreachable. Keep Product price read-only on this screen and outside its mutation payload. Numeric 13-digit values require a valid EAN-13 check digit in both frontend and backend; generated codes default to internal prefix `200`, expose `885` only with a GS1-allocation warning, preflight duplicates, and retain the database unique key as the race guard. Preview/print only standards-encoded bars—never decorative fake stripes.

- **No Company Availability Editors**: Do not render or save `businesscodes[]`/`companyguids[]` on company-owned masters. The global workspace bar already shows the active company. - **Minimal Barcode UX**: Barcode create/edit shows Product link/quick Product name, barcode, unit, conversion, main status, exact decimal prices, and optional Barcode-owned images/videos/description for that package or unit. Put Product-master details on Product screens. Never show or edit Barcode quantity, balance, cost, min/max/order point, classification, marketplace/logistics, BOM, or raw JSON. Product detail must show Product-owned media and same-company linked Barcode media as separate read-only groups without copying between records. Quick create must return a linked minimal Product before the record is usable for sale/receipt/stock.
- **Marketplace SKU Dimension Availability**: Product/SKU marketplace screens should store channel-specific dimension availability in `marketplaceskumappings[].marketplacedimensionstocks[]` (legacy underscore keys `marketplace_sku_mappings`/`marketplace_dimension_stocks` are compatibility only) and render it as marketplace availability projection only. Do not expose it as accounting stock, costing, or warehouse balance.
- **Add Copy Buttons**: Editable CRUD/list screens should show `คัดลอก` beside `เพิ่ม` when a selected row can be duplicated. Style both buttons with the same primary treatment, open create mode instead of edit mode, and prefill the form from the selected row as completely as possible.
- **Standard List Toolbar**: Master-data list screens should include search, `ตัวกรอง`, `รูป` when images exist, `เลือกเพื่อลบ`, a selected-row multi-delete button, and a visible total count. Do not put edit/delete icon buttons inside list rows when the right-side detail panel already contains edit/delete actions.
- **Product List Datalist Source**: Product datalists read rows from the company-scoped PostgreSQL `product` projection, then hydrate MongoDB detail by `(businesscode,code)`. Never synthesize `guidfixed = code`; rebuild the projection from same-company MongoDB `products`, never from `productbarcode`. Every Barcode already links a Product.
- **Projection Query Safety**: Product/list projection queries must only reference columns and tables verified in source or runtime schema. Optional list display fields should return typed default literals or be conditionally joined, so a missing projection column does not make the whole screen show `โหลดข้อมูลไม่สำเร็จ`.
- **Product List Units & Balance**: Product master lists should include `ประเภทหน่วยนับ` and `ยอดคงเหลือ`. Display unit type as `หน่วยนับเดียว` or `หลายหน่วยนับ`, and format product/accounting balance with auto-packing from larger units to smaller units, such as `4 ลัง x 2 โหล x 45 ชิ้น`.
- **Product Units And Barcode Matches**: Keep one required top-level Product standard unit visible with disabled `1:1`; allow replacement through the unit picker but never clear/delete it. Store removable additional rows only in `unitconversions[]` as unit code/name plus positive integer ratio—never ask for or persist a Barcode in a unit row and never use `isusesubbarcodes` as a multi-unit toggle. Show matching Product `barcodes[]` read-only under each unit by normalized `barcode.itemunitcode === unit.unitcode`, including the base unit. Block save on blank/duplicate unit codes or invalid ratios.
- **Mobile/Computer Product Screens**: Mobile phone, SIM, computer, and serialized electronics menus must expose structured `ทะเบียนเลขเครื่อง` and `ราคาตามช่องทางขาย` screens. Use normal form fields for serial/IMEI/ICCID, status, product/barcode/SKU, warranty, channel, price, date range, and sync settings; never make normal users edit these as JSON.
- **Route-Matched Screen Labels**: Page titles, subtitles, detail headers, empty states, aria labels, and toolbar context must match the active route/menu. Reuse shared dictionaries only for field labels unless the screen-level words are explicitly correct for that route.
- **Cross-Screen Drill-Down**: A button that opens a related master screen must carry the normalized business key through the existing tab/router state with a one-shot request ID. The destination selects that exact key and must not fall back to the first row while the requested record is absent or loading; preserve the unsaved-change confirmation before switching records.
- **MongoDB Model Graph Scope**: The data-model graph is a read-only browser for source-backed MongoDB structure. Show root documents/collections plus every reachable nested or `bson:"inline"` structure from field-table links, including shared models under `backend/internal/models`; hide unrelated request/response DTOs, PostgreSQL projections, narrative-only references, note editing, and graph-decoration controls. UI labels follow the active BC Ai Account language, while technical model names, field names, bson/json keys, collection names, and source paths remain unchanged.
- **No Duplicate Workspace Context In Headers**: Do not show selected company/branch badges inside individual screen headers because the global workspace bar already shows them. Keep company/branch controls only when they are real workflow data, filters, access scopes, or legal/branch setup fields.
- **Promotion Menu Placement**: `โปรโมชั่น` belongs under `ตั้งค่าการขาย` because it affects selling conditions. Do not place it in the core product/barcode group.
- **Workspace Company Cards**: Company-selection cards must use metadata already returned by `/list-shop` or the local workspace proxy. Do not depend on `/shop/:id` before `select-shop`, because shop detail endpoints require an active selected shop and will otherwise fall back to incomplete language/currency/date values.
- **Workspace Company & Branch Selection**: When a company is selected, the system must verify the branches. If no branch exists, it must automatically create the head-office branch (`00000` named "สำนักงานใหญ่"). The frontend must transition to the branch selection step (`step = "branches"`) in all cases, ensuring the user manually selects the branch, even if only a single branch is available. Automatic bypass of this selection step is prohibited.
- **Multilingual Data Fields**: `names`, localized addresses, and equivalent localized business fields must render exactly the active company languages from `settings.languageconfigs` in order. Normal data forms must not have add-language controls. Read legacy `settings.languageconfigs` only as a transition alias. Reducing active languages hides inputs only and must preserve hidden-language values on load/save. Do not auto-fill or fallback one business-data language value from another language.
- **Semantic Backgrounds**: Every major page needs a page-specific `.webp` background that communicates that screen's domain. Assets must be photorealistic, premium-camera quality, physically plausible, include presentable professional Thai people when natural for the page, and have clear depth of field. Generate new background images with a real raster image-generation tool (the running agent's image_gen capability), Read-verify, then wire the approved `.webp` asset. Never hand-draw vector/SVG as a substitute; if the running agent has no image-gen tool, ask Jead.
- **Language Switch**: Flags themed grid (2 columns) for adding languages. Drag-to-reorder rows (first row is primary).
- **Custom Indicators**: High-contrast SVG/CSS styled boxes for read-only checkboxes (avoid disabled native checkboxes that are hard to read).
- **Media Previews**: Authenticated fetch for `/goapi/s3/file/...` to render browser-local object URLs (cache images and video JPG posters in session memory; load private MP4 blobs only on demand). Product/Barcode video cards show the still poster plus a clear play action before playback. Image/video cards and galleries in normal edit/read-only/detail screens show the media, empty state, or friendly load error only; never print the stored URI/path under or beside it. Keep raw paths inside state/API and expose them only in an explicit technical/admin diagnostic view.
- **Timezone Display = branch timezone (set 2026-06-22)**: Backend/DBs store all timestamps in **UTC+0**; the frontend CONVERTS UTC → the active branch's `timezone` (e.g. `Asia/Bangkok`) for display. Always render business dates/times through `frontend/src/lib/date-time.ts` (`formatDefaultDate`, `formatDefaultDateTime`, `resolveWorkspaceDateTimeDisplayOptions`) using the active workspace/branch timezone — never browser-default `Date.toLocaleString()`/`toLocaleDateString()`/ad hoc `Intl.DateTimeFormat` in screens. Treat API timestamps as UTC ISO-8601 (`Z`). See core-rules "Timezone Iron Rule" + "Project Date Display Contract".
- **Next Image Aspect Ratio**: When styling `next/image`, do not change only width or only height through CSS. Keep CSS dimensions consistent with the `width`/`height` props, or set the complementary dimension to `auto` only when the other dimension is intentionally resized and verified not to trigger Next.js aspect-ratio warnings.
- **Hydration Errors**: Check `mounted` state in `useEffect` before rendering window/client-side dynamic styles.
- **Root Bootstrap**: Prefer server-rendered attributes/styles plus cookie-backed client sync for theme or app bootstrap that can be represented without JavaScript. Use Next.js `next/script` with explicit `id` and `beforeInteractive` only when a script is genuinely required and verified not to trigger React/Next runtime warnings. No raw `<script>` tags.
- **Leading Icon Inputs**: When an input has an absolutely positioned leading icon such as `Search`, set the icon to `pointer-events-none` and use important left padding such as `!pl-10` on the shared `<Input>`. Plain `pl-8`/`pl-9` can be overridden by the shared Input base `px-1` and make text/placeholder overlap the icon.

## 7. Pre-Commit Verification
- Fast-iteration dev mode: rely on `next dev` HMR while iterating. Run `npm run typecheck` in `frontend/` only before commit or when summarizing — not after every edit.
- Verify in both Light/Dark themes and check responsiveness in this priority order: **iPad/tablet (`md:768px`+) first → notebook (`lg/xl`) → desktop (`2xl`) → mobile (`<768px`) last**. Most verification time should go to iPad/notebook where BC Ai Account's Thai SME users actually work. Mobile only needs a quick "does not break" check.
