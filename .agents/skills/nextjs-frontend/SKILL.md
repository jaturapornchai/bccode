Target app: `D:\bccode\frontend`.

Read `D:\bccode\AGENTS.md` first; it is the full source of frontend, language,
theme, responsive, manual, security, and context-budget rules.

Fast workflow:
- Inspect only the relevant route/component/lib/test files.
- Use `rg` so `.ignore` excludes generated docs, dependencies, legacy Flutter,
  manuals, binaries, and duplicate skill bundles.
- For migration, clone, redesign, or reference-screen work, first inspect the
  matching Flutter screen under `D:\bcdev\frontend\bcaiaccount` and any
  user-provided screenshot/reference screen. Preserve the user-facing workflow,
  labels, menu hierarchy, actions, states, permissions, and API/data intent in
  the Next.js implementation.
- If the matching Flutter screen cannot be found, report the searched paths
  instead of guessing the workflow.
- Do not read `languages.tsv` fully; query exact keys only.
- Use backend language/i18n for visible text. During UI iteration, stable keys are required; when a key is missing, show an explicit missing-translation error and record it under `backend/prompts/language_requests/` for later batch-editing in `languages.tsv`.
- When a loaded backend language dictionary is missing a menu/UI key, show a visible missing-key error instead of a local label, raw slug, or silent substitute text.
- Keep frontend web compatible with the backend API version contract. The current backend baseline is `v1`; future versions such as `v2` must run side-by-side with `v1`, and frontend API callers must know and send the required backend version metadata when version-aware APIs are involved.
- For active/configured language management, the add-language action must open a themed language choice dialog first. Do not show a native select/combobox beside the add button or add a default/preselected language without an explicit user choice.
- Active/configured language rows must be reorderable freely by holding and dragging anywhere on the row with a visible animated movement state; do not use separate up/down move buttons. The first row after reordering becomes the primary/default language, and the editor must keep at least one language.
- Company localized-name fields must use the configured active company languages and order from `settings.languageconfigs`; do not fall back to a single default language when editing the company screen.
- Branch tax code inputs must follow the central Thai Branch Code Rule: show the five-digit legal code, normalize aliases/numeric shorthand before submit, and surface validation errors beside the save flow. Frontend normalization is for UX only; backend remains the source of truth.
- Thai branch address inputs must use the backend dataset endpoint through `frontend/src/lib/thailand-addresses.ts`; keep the full JSON out of `frontend/public`, load via the configured Backend URL/proxy, and keep province/district/subdistrict cascading plus postal-code reverse lookup together. Store codes in form payloads, not display names. Recompute `zip_code` on province/district/subdistrict changes: use a district postal code only when unique or already matched, set exact zip on subdistrict, and clear stale invalid zip values.
- Branch structured settings such as `paymentrounding` and `pointconfig` must follow the legacy Flutter workflow and render editable and read-only tables/forms, not raw JSON editors, raw JSON detail dumps, or JSON toggle buttons. Keep the persisted payload shape compatible with the backend JSON fields.
- Product category (`/product_category_group_select_screen`) must follow the legacy Flutter workflow: compact full-width group-number selector, hierarchical category tree, row actions for add child/edit/delete, animated drag/drop reorder, and an inline detail editor for `names`, `parent_guid`, `group_number`, `useimageorcolor`, `colorselecthex`, `imageuri`, `coveruri`, and `timeforsales`. The group selector must use dense full-width flex-wrap button/chip rows that show all 20 groups with minimal vertical space, not fixed-column grids or tall card grids. Compute the group card width from the available container width before rendering stable rows; all group cards must share the same width and the final wrapped row must not stretch wider than earlier rows. Before a group is selected, its parent layout must not constrain the selector to the left/detail column; the selector must occupy the full content width. After a group is selected, search/add/back controls must be lifted into the main screen header next to the title/action controls, not rendered as a separate toolbar/card above or inside the tree. The selected group layout must stretch the tree pane and detail/editor pane to the same full available height. Category rows must use pointer-based hold-and-drag from anywhere on the row, with interactive buttons excluded including SVG/icon descendants, because native HTML `draggable` alone does not satisfy the Flutter-style hold/move behavior. During drag, keep the original row as a placeholder and render the moving row as a viewport-level overlay following the pointer, matching the dnd-kit DragOverlay pattern for scrollable/long lists. Sibling rows must swap live with FLIP animation as the pointer crosses their before/after zones; show clear labels for "Drop before" / "วางก่อน", "Drop after" / "วางหลัง", "Drop child" / "วางเป็นลูก", and root drop. While dragging, attach window-level pointermove/up/cancel listeners so pointer release is not lost when live preview reorders rows under the cursor. On pointer release, recompute the drop target from the final pointer coordinates instead of trusting only the last pointermove state, so fast drag-and-release still drops predictably. The root drop target must render at the bottom of the tree pane, not above the first row. Dropping on the root target moves the category back to the root/top-level category list, clears `parent_guid`/`parentguidall`, appends it after the current root categories, and persists the affected `xsort` values. Normal row drops are reorder-only: top half inserts before, bottom half inserts after, and the row center must never implicitly move an item as a child. Moving as a child requires an explicit visible child-drop target such as "Drop child" / "วางเป็นลูก", then persists `parent_guid`, `parentguidall`, and affected `xsort` values through the real API. Drag/drop must feel smooth and easy to understand: apply live preview order updates while dragging, apply optimistic in-memory order/parent updates immediately on drop, animate row layout changes with a FLIP-style transform for reorder, move-to-child, move-to-root, expand, and collapse, do not call full refresh after successful reorder/move, and only refresh after a save failure to restore server truth. Any immediate edit/detail action after drag must receive the optimistic parent/order values, not stale source records. Selected rows must not change indentation or padding; use non-layout-affecting indicators such as absolute bars so child rows stay in their original level position. Category rows must show the immediate child count as a real expand/collapse button, wrap long names instead of truncating them, and the tree container must use auto height with the outer page pane handling scrolling instead of a fixed `max-h` inner scrollbar. Do not restore up/down move buttons, do not fake reorder only in UI, do not rely only on native drag events for row movement, and do not regress this screen to a generic CRUD list, hidden form branch, or raw JSON editors for category internals.
- The `/branch` screen is the single entry point for branch-scoped data. It renders as a master-detail layout: a sticky branch list on the left and a tabbed editor on the right with these tabs: General, Address, Department, Work Day, Holiday, POS/Tax, Business Types. Department, Work Day, and Holiday must not appear as their own sidebar menu items — they are embedded tabs that scope to the currently selected branch.
- Embedded sub-screens reuse the existing `SystemSettingsScreen` component with `branchOverride` and `hideChrome` props so they share `loadRecords`, `saveRecord`, and field rendering instead of duplicating logic. `branchOverride` swaps the active branch in the workspace memo without persisting back to `localStorage`, so the embedded screen sees the right `dateTimeScope`, branch query params, and per-branch payload context.
- Branch latitude and longitude render together as a compound field with an inline "เลือกจากแผนที่ / Pick on map" button. The map dialog is full screen, uses Leaflet + OpenStreetMap (free, no API key), and provides Nominatim search and a current-location button. Default position uses the existing lat/lng when present, otherwise Bangkok (13.7563, 100.5018). The dialog writes both coordinates back to the form rounded to 6 decimal places. Do not switch to Google Maps, Mapbox, or other providers without explicit approval — those require API keys and incur billing.
- Frontend image upload proxies must use GoAPI R2 storage through `POST /goapi/image/upload`, not legacy `/upload/images` Azure Blob routes. Normalize successful upload metadata to a frontend URL under `/goapi/s3/file/...` so previews and saved image fields do not depend on direct R2/Azure URLs. If R2 config or upload category is missing, surface the backend/client error; do not choose another storage path, default category, derived credential, or standalone Cloudflare token silently.
- Read-only/detail and edit views for `image-upload` and `image-gallery` fields must render the actual image preview and keep the stored URL/path fully visible. Protected GoAPI/R2 paths must be loaded with authenticated `fetch` and rendered as browser-local object URLs because browser image requests cannot attach bearer auth. The detection helper must match every routing surface the same backend can appear under — direct (`/goapi/s3/file/...`, `/s3/file/...`), proxied (`/backend/goapi/s3/file/...` for same-origin Next.js + Caddy rewrites), and absolute (`http(s)://host/.../s3/file/...`). Use a single check such as `pathname.includes("/s3/file/")` so future deploy paths and custom origins do not bypass the auth fetch. Reuse object URLs only in memory for the current frontend session to keep private images fast without public URLs or persistent browser storage. If the image fails to load, show the original stored value as an explicit failure state; never show only a raw URL when a preview can be rendered.
- Fields that store many images must use the `image-gallery` field type (form value is `string[]`). The branch screen uses `imageuris` for the multi-image gallery while keeping the legacy `imageuri` single string as a backward-compatibility seed: when a record has empty `imageuris` but a non-empty `imageuri`, `formFromRecord` seeds `imageuris = [imageuri]` so the editor can render existing data; subsequent saves write only `imageuris`. The backend `Branch` model carries both `ImageURI string` (legacy) and `ImageURIs []string` (canonical going forward).
- Save actions must leave a visible result near the save surface: success should say saved successfully, and failures should include the real API/client reason.
- Expected API failures that are already rendered in the UI should not be re-thrown or logged with `console.error` in client components. Parse JSON error responses into the visible message, keep console clean for unexpected defects, and refresh/reload only when server truth must be restored.
- Keep UI dense, mobile-first, full-width/wrap-first, and theme-aware.
- Top-level screen controls that contain language, theme, menu layout, or account preferences must remain visible while scrolling; do not auto-hide them behind content scroll.
- Preserve the above-the-fold density contract from `D:\bccode\.agents\rules\bc-account-core-rules.md`: topbar, category/menu row, open-tab strip, screen header, and search/action toolbar must remain compact. Use `h-8`/about 32px controls where practical, low padding/gaps, compact tab rows, and wrap-first action rows. Do not restore tall headers, large tab cards, or `h-10`/`h-11` utility controls in these zones unless Jead explicitly asks.
- **Display Integrity & No Truncation**: Displayed data, labels, fields, IDs, and metadata (e.g., shop IDs, creator details, company names) must be fully visible and readable. Do not truncate, clip, hide, or discard displayed information using ellipsis. Ensure wrapping is enabled (`word-break: break-word` and `white-space: normal`).
- **Entity Card Layouts**: Widen card grid column minimum widths (e.g., to at least 480px) and arrange sub-details horizontally using flex rows (`.shop-details-row`) to prevent layout clipping and vertical text wrapping.
- For screens, minimize page margins, section padding, gaps, field spacing, table/list row height, and control height through shared CSS/tokens first, so the viewport shows more real business data. Keep touch targets usable, but do not add decorative whitespace.
- Prefer wrapping toolbars/tabs/forms/lists over horizontal overflow. Prevent horizontal scrollbars on lists, tables, and pages by using responsive columns (hiding less critical columns on narrower viewports) and flex-wrap layouts, ensuring all content adjusts cleanly to fit the viewport width. Before opening popups, dropdowns, or menus, calculate their size and position from the trigger and current viewport/container so they do not overflow off the right edge.
- In multi-level or flyout menus, calculate and set the vertical positioning of submenu containers (e.g., Column 2 or Column 3) dynamically so that their top edge aligns directly with the active/hovered trigger button's row (for example, using a calculated `top` offset based on index and item height) rather than resetting to the top of the container.
- Flatten navigation structures to prevent deep nesting and reduce clicks: if a menu section contains only a single group (e.g. "ตั้งค่าระบบ" inside the Settings section), bypass the redundant intermediate group button/header. Render the nested items/folders directly under the parent section in sidebar accordions, and directly in Column 1 in top dropdown flyouts.
- Use native browser scrolling for scrollable panes, lists, tables, dropdowns, dialogs, and popup columns. Apply the project global scroll rules (`overflow-y-auto` or `overflow-auto`, `overscroll-contain`, touch momentum support) so Mac two-finger trackpad scrolling and mobile finger scrolling work without custom wheel/touch handlers.
- Store UI-only preferences that are personal to the current browser, such as left-menu vs top-menu layout, in `localStorage`, not the database. Scope preference keys by user identity and backend when multiple users can share one device. If an old global key must be migrated, implement an explicit one-time migration path and make the source clear in code; do not silently substitute preference values.
- **Read-Before-Modify & No-Reversion**: Always read the target file's latest state using `view_file` before editing. Do not revert premium UI improvements, layout refactoring, or spacing adjustments from previous steps.
- **Checkbox Column Layout**: For settings matrices and checklists (e.g. permission lists), organize checkboxes horizontally side-by-side using responsive columns (`grid grid-cols-2 sm:grid-cols-5`) and override global stylesheet overrides by adding `inline-flex w-auto max-w-none` to labels, rather than stacking checkboxes vertically.
- **Read-Only Custom Contrast Indicators**: In detail views or preview panels, avoid using native `<input type="checkbox" disabled />` since browsers force-fade them to an illegible light gray. Use custom CSS/SVG high-contrast indicators styled using theme variables to keep them readable.
- Prefer existing components and patterns; do not copy Flutter scaffolds.
- **Hydration Mismatch Prevention**: When using client-side layout adjustments (e.g. resizable panels calculating widths or inline styles based on `window`), wrap them with a `mounted` state check initialized in `useEffect` so that the initial HTML sent by the server exactly matches the client's hydrated HTML, avoiding hydration errors.
- Root layout boot scripts such as theme/color initialization must use Next.js `next/script` with an explicit `id` and an appropriate strategy such as `beforeInteractive`. Do not render raw `<script>` tags directly inside React components/layouts because React will warn and the script may not execute on client render.
- Verify with `npm run typecheck`, focused `npm run lint -- <files>`, focused tests when present, and browser checks for desktop plus a narrower/mobile viewport when scrolling or responsive layout changed. For top-chrome/density changes, capture screenshot or bounding-box evidence for the topbar/menu/tabs/header/search-toolbar heights.
