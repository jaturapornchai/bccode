# ข้อมูลตัวอย่าง GL ร้านวัสดุก่อสร้าง ปี 2569

ชุดข้อมูลสมมติสำหรับสาธิตระบบบัญชีแยกประเภท ไม่มีชื่อบุคคล เลขบัญชีธนาคาร หรือเลขประจำตัวผู้เสียภาษีจริง **นำเข้า production แล้วเมื่อ 11 กันยายน 2026 เวลา 18:18 น.** ใน holding `demo` บริษัท `C01` สาขา `00000` ผ่าน MongoDB → Kafka → PostgreSQL ของ GL

## ไฟล์

- [ยอดคาดหวัง](gl-thai-construction-2026-expected.json): งบทดลองรายบัญชี งบกำไรขาดทุน งบฐานะการเงิน กระแสเงินสด และตารางประกอบ

## เปิดดูข้อมูลบนเว็บ

เปิด [BC Ai Account](https://account.bcaicloud.com/) → **ทดลองใช้ระบบ** → **กลุ่มกิจการรุ่งเรือง (สาธิต)** → **บริษัท รุ่งเรืองวัสดุก่อสร้าง จำกัด** → **สำนักงานใหญ่** แล้วเปิดระบบบัญชีแยกประเภท

เลือกปี `DEMO2569` และช่วง `01/09/2026`–`11/09/2026` เพื่อดูงบทดลองและกำไรขาดทุน; ประมาณการกระแสเงินสดเลือก `15/09/2026`–`30/09/2026` ใบ `DEMO-BM69-JV-DRAFT-001` ยังคงเป็นร่างสำหรับทดลองตรวจปูนเสียหาย จึงไม่กระทบยอดรายงาน

ข้อมูลตัวอย่างคงไว้ให้ทดลอง ไม่ใช่ข้อมูลชั่วคราวที่ลบทิ้งหลังทดสอบ การแก้เอกสารที่ผ่านแล้วต้องใช้รายการกลับ/ปรับปรุงตามขั้นตอนระบบ

## เรื่องราวธุรกิจ

ยอดยกมา ณ 1 มกราคม 2026 มีเงินสด ธนาคาร ลูกหนี้ สินค้า สินทรัพย์ หนี้สิน ทุน และกำไรสะสม ตั้งแต่ 1–10 กันยายนมีซื้อปูน เหล็ก และสี ขายเชื่อให้โครงการสมมติ ขายสด รับชำระลูกหนี้ จ่ายเจ้าหนี้ รับคืนสินค้า คืนสินค้าผู้จำหน่าย ค่าไฟฟ้า น้ำมัน เงินทุนเพิ่ม ซื้ออุปกรณ์ ผ่อนเงินกู้ ค่าเสื่อมและตัดประกันล่วงหน้า ครบสมุด `UV/SV/RV/PV/JV` โดยยึดชื่อสมุดใน source ของ BC: `UV` = รายวันขาย, `SV` = รายวันซื้อ (`frontend/src/lib/general-ledger.ts:48`)

ใช้สินค้าคงเหลือแบบต่อเนื่อง: ซื้อเพิ่มสินค้าคงเหลือ, ขายบันทึกต้นทุนขายพร้อมลดสินค้า, รับคืนเพิ่มสินค้าพร้อมลดต้นทุนขาย แต่ละสินค้าสมมติมีต้นทุนต่อหน่วยคงที่ ใบร่างตรวจปูนเสียหาย 3 ถุง วันที่ 11 กันยายนยังไม่ลดสินค้าและยังไม่เข้ากำไรขาดทุน

ภาษีซื้อและขายใช้ 7% สำหรับวันในตัวอย่าง อ้างอิง[ข่าวกรมสรรพากร 34/2568](https://www.rd.go.th/fileadmin/user_upload/news/2568thai/news34_2568.pdf) จำนวนเงินที่เลือกคำนวณได้พอดีสองตำแหน่ง ไม่มีส่วนต่างปัดเศษ กำหนดนโยบาย `ROUND_HALF_UP` ที่ยอดภาษีต่อเอกสารเพื่อให้วิธีสร้างข้อมูลชัดเจน ไม่สร้างเงินเดือน ภ.ง.ด.1 หรือรายการปิดปี

## วิธีนำเข้าและส่งคำขอซ้ำอย่างปลอดภัย

1. ตรวจบริษัทและสาขาที่ได้รับอนุญาต ตรวจว่าไม่มีรหัสปี/งวดทับช่วงหรือรหัสข้อมูลตัวอย่างซ้ำ ห้ามทับข้อมูลเดิมหรือเปลี่ยนปีเดิมโดยอัตโนมัติ
2. ใช้ GL command API สร้างกลุ่มผังบัญชี → ผังบัญชีตามลำดับในไฟล์ → ปีบัญชี → งวด → กลุ่มบัญชีสินค้า → งบประมาณและ forecast แต่ละ payload อยู่ใต้ key ที่สัมพันธ์กับ `resource`; อย่าส่ง wrapper ของ fixture ทั้งก้อนไปยัง API
3. สำหรับ `journals[]` ส่งเฉพาะ `journal` ด้วยคำสั่ง create; `post`, `businessfacts`, `expecteddebit`, `expectedcredit` เป็นคำอธิบายของ fixture ไม่ใช่ field ของ Journal API
4. ถ้า `post: true` ให้ส่งคำสั่ง post แยกโดยใช้ ID และ version ที่ได้รับจาก create ถ้า `post: false` ให้คงร่างไว้ ใช้ request ID คงที่และต่างกันต่อคำสั่ง เพื่อ retry โดยไม่สร้างข้อมูลซ้ำ
5. บันทึกผ่าน API ให้ MongoDB เก็บต้นทางและส่งต่อ Kafka ตามกลไกระบบ รอ PostgreSQL projection ครบก่อนตรวจรายงาน ห้ามเขียน MongoDB/PG โดยตรงเพื่อข้าม audit, validation หรือ outbox
6. รายงานจริงใช้ `fiscalyear=DEMO2569&from=2026-09-01&to=2026-09-11&branchcode=00000` ช่วงนี้รวมวันที่ใบร่างด้วย แต่ใบร่างต้องไม่กระทบยอด actual ส่วน forecast ใช้ `from=2026-09-15&to=2026-09-30`

API คำสั่งอ้างอิง `backend/internal/generalledger/httpapi/http.go` ที่ `/gl/v2/command`; ดำเนินการหลังระบบ Kafka และสิทธิ์ผู้ใช้พร้อมเท่านั้น

## การตรวจที่ทำแล้วและข้อจำกัด

- Generator ตรวจด้วย Python `Decimal`: เดบิตเท่ากับเครดิตทุกใบ, stock ไม่ติดลบและตรงบัญชีคุม, AR/AP ตรงตารางจัดสรร, สินทรัพย์ = หนี้สิน + ทุน
- ตรวจด้วย `Account.Validate`, `FiscalYear.Validate`, `Journal.Validate` จาก Go source จริง: ผ่าน 38 บัญชี, 12 งวด, 17 ใบที่จะ post และ 1 ใบร่าง
- JSON amounts เป็น decimal strings, BSON round-trip ผ่านชนิด Decimal128 ทั้ง master และ journal; Go Decimal คำนวณตรงยอดคาดหวัง 31 บัญชีที่มีรายการ
- นำเข้าจริงผ่าน API 110 คำสั่ง: ตรวจ MongoDB ทันทีและอ่านกลับจาก PG ทุกขั้น ผ่านทั้งหมด; 5 รายงานตรงยอดคาดหวังและทดลองส่งคำขอเดิมซ้ำ 2 รายการโดยจำนวนข้อมูล/เหตุการณ์ไม่เพิ่ม; outbox pending เป็นศูนย์ ดู [หลักฐานทีละขั้น](../evidence/2026-09-11-gl-kafka/seed-verification.json)
- ตรวจอิสระฐานข้อมูลจริง: MongoDB/PG มีข้อมูลธุรกิจ 93 รายการ, เหตุการณ์ไม่ซ้ำ 110 รายการ, บัญชีที่ผ่านแล้ว 77 บรรทัด เดบิต = เครดิต `1,953,100.00` ทุกบัญชีตรง fixture; Mongo pending และ Kafka lag เป็นศูนย์ จำนวนข้อมูลบริษัทอื่นเท่าเดิม ดู [ผลกระทบยอด](../evidence/2026-09-11-gl-kafka/production-reconciliation.json)
- ตรวจเว็บรุ่นสุดท้าย `r20260911-gl-demo-thai-1`: รายงาน 5 ชุดและเมนู 35 เส้นทางผ่าน; ตรวจภาพรายงานสว่าง/มืด 16 แบบ รวมงบทดลองที่ 1600/1280/1024/768 พิกเซล หมวดบัญชี/สถานะ/ประเภทเงินเป็นภาษาไทยและชื่อกำไรขาดทุนที่ยังไม่ปิดชัดเจน โดยทดสอบอ่านอย่างเดียว ไม่มี console error ของ GL
- `stockmovements`, `inventoryschedule`, `arallocations`, `apallocations`, `businessfacts` เป็นตารางประกอบกระทบยอด GL ไม่ได้สร้างทะเบียนสินค้าหรือเอกสารซื้อขายในโมดูลเดิม
- ค่าเสื่อมและประกันเป็นตารางสมมติสำหรับเดือนกันยายน ไม่ได้อ้างว่าเป็นการประเมินภาษีจริง อุปกรณ์ซื้อใหม่ในวันที่ 10 กันยายนยังไม่คิดค่าเสื่อมในชุดนี้ ยอดภาษีซื้อ/ขายยังแยกบัญชีและไม่สร้างรายการนำส่ง

สร้างไฟล์ซ้ำได้จาก project root ด้วย `python docs/examples/gl-thai-construction-2026-generate.py` ต้องการเพียง Python 3 standard library

Schema และ validation อ้างอิง `backend/internal/generalledger/models.go`, `amount.go`, `mutations.go`; สูตรรายงานอ้างอิง `reports.go` และ `reports_operations.go` โดยไม่ปรับ runtime source เพื่อรองรับตัวอย่าง
