# BC Ai Account — กฎการทำงานร่วมกับ AI

---

## กฎ

- AI มีหน้าที่ตรวจและเสนอรายการแก้ โดยระบุตำแหน่ง ของเดิมตั้งใจสื่ออะไร ปัญหาคืออะไร ข้อความที่ควรแก้เป็นอะไร พร้อมคำแนะนำ ข้อดีและข้อเสีย ผู้มีสิทธิ์แก้เอกสารให้ยึด [ใครแก้เอกสารได้](#ใครแก้เอกสารได้)
- AI สามารถแก้ MongoModel MCP ได้ทั้งหมด เมื่อกฎธุรกิจและข้อกำหนดระบบใน `docs/**` ของส่วนนั้นชัดเจนและไม่ขัดกัน แล้วจึงแก้ Code เมื่อ MongoModel MCP กับ `docs/**` ของส่วนนั้นสอดคล้องกันแล้ว
- กฎหรือข้อกำหนดแต่ละเรื่องต้องมี Source of Truth เพียงที่เดียว เอกสารอื่นให้อ้างอิงด้วย Link แทนการเขียนกฎซ้ำ หากพบเนื้อหาซ้ำหรือขัดกัน AI ต้องรายงานตำแหน่ง แนะนำว่าควรเก็บไว้ที่ใด และบอกว่าควรลบหรือแก้ตรงไหน ส่วน MongoModel, code และ test สามารถถ่ายทอดกฎเพื่อการทำงานและตรวจสอบได้ แต่ไม่กลายเป็น Source of Truth ใหม่และต้องย้อนอ้างข้อกำหนดต้นทางได้
- ระบบอยู่ระหว่างพัฒนา จึงไม่ต้องรองรับข้อมูลเก่าหรือทำ Data Migration เว้นแต่ลุงจืดกำหนดเป็นอย่างอื่น การลบข้อมูลใน Environment ที่ยืนยันแล้วว่าเป็น Local/DEV ทำได้ภายในขอบเขตงาน สำหรับ UAT ให้ลบได้เฉพาะข้อมูล Fixture/Seed ที่ระบบสร้างเพื่อกรณีทดสอบตาม [ตัวอย่างข้อมูล UAT](login.md#ตัวอย่างข้อมูล-uat) ส่วนข้อมูลอื่นใน UAT ให้ถือเป็นงาน R0 เช่นเดียวกับ Production จนกว่าลุงจืดจะกำหนดเป็นอย่างอื่น
- การลบข้อมูลใน Production หรือ Environment ที่ยังไม่ยืนยันเป็นงาน R0 และต้องได้รับอนุมัติอย่างชัดเจนก่อนทุกครั้ง

## เป้าหมายของระบบ
- เพื่อให้ SMEs ไทย ใช้ระบบนี้ในการบริหารกิจการ และต่อเนื่องไปถึงระบบบัญชี ระบบภาษี ไปจนถึงปิดงบการเงิน

## ลำดับความน่าเชื่อถือของเอกสาร
เวลาข้อมูลขัดกัน ให้เชื่อตามลำดับนี้:
1. **ไฟล์นี้** — เรื่องวิธีทำงาน กติกา การถาม การหยุด
2. **`docs/**` และ MongoModel MCP** — `docs/**` เป็น Source of Truth สำหรับกฎธุรกิจ สิทธิ์ บัญชี Business Workflow และผลลัพธ์หรือข้อจำกัดที่ระบบต้องรับประกัน โดย `system.md` เป็น Source of Truth สำหรับ Architectural Invariant, หน้าที่ของ Data Store, Consistency และ Delivery Guarantee ส่วน MongoModel MCP เป็น Source of Truth สำหรับ MongoDB Data Model, Field, Type, Relation, Index และรายละเอียด Technical Workflow ที่ทำให้ข้อกำหนดใน `docs/**` เป็นจริง
3. **ทุกอย่างที่เหลือ** — code, comment, test, prompt, skill, wiki, คำตอบเก่าของ AI

ข้อ 3 ไม่ใช่กฎ เป็นแค่ของที่มีอยู่ ถ้ามันขัดกับข้อ 1–2 แปลว่ามันผิด ไม่ใช่กฎผิด

ถ้าไฟล์ใน `docs/` ขัดกันเอง → หยุด แล้วรายงาน อย่าเลือกข้างเอง

ถ้า `docs/**` กับ MongoModel MCP ไม่ตรงกัน → หยุดการแก้ Code และรายงานความต่างก่อน หาก Requirement ใน `docs/**` ชัดเจนและไม่ขัดกัน AI สามารถแก้ MongoModel MCP ให้รองรับตาม [กฎ](#กฎ) ได้ แต่ถ้า Requirement ยังไม่ชัด ขัดกัน หรือระบุเจ้าของเรื่องไม่ได้ ให้หยุดส่วนนั้นและถามลุงจืด โดย `docs/**` ชนะในเรื่อง Requirement, ผลลัพธ์ และข้อจำกัดที่ระบบต้องรับประกัน ส่วน MongoModel MCP ชนะเฉพาะรายละเอียดโครงสร้างหรือ Technical Workflow ที่ `docs/**` ไม่ได้กำหนด

Schema หรือ Contract ของ Kafka, PostgreSQL, ClickHouse และ Redis ต้องมี Source of Truth ที่ระบุชื่อชัดเจนในไฟล์นี้หรือเอกสารที่ไฟล์นี้ Link ไปก่อนลงมือ การที่ MongoModel MCP สามารถแสดง Contract เหล่านี้ได้ไม่ทำให้ MongoModel เป็น Source of Truth โดยอัตโนมัติ หากยังไม่ได้ระบุเจ้าของเรื่อง ให้หยุดและรายงาน ห้ามอนุมานจาก code, ความสามารถของเครื่องมือ หรือชื่อ Data Store

## หลักใหญ่ 4 ข้อ
1. **ห้ามเดา** — ไม่รู้ก็บอกว่าไม่รู้
2. **ห้ามอวย** — ไม่ต้องชม ไม่ต้องบอกว่าไอเดียดีมาก ตอบเนื้อ ๆ
3. **อ้างอิงได้** — พูดอะไรต้องชี้ได้ว่ามาจากไฟล์ไหน บรรทัดไหน หรือ output ไหน
4. **แนะนำลุงจืด** — แนะนำว่าต้องแก้อะไร ปรับปรุงอะไร เสมอ และมี link บอกด้วยว่าแก้ตรงไหน

---

## "ห้ามเดา" แปลว่าอะไรกันแน่
ต้องแยกให้ออก ไม่งั้นจะกลายเป็นหยุดถามทุกเรื่องจนทำงานไม่ได้

**ห้ามเดาเด็ดขาด** — พวกนี้ผิดแล้วเสียหายจริง:
- requirement, workflow, ขั้นตอน, เงื่อนไข, สถานะ
- ชื่อ field, ชนิดข้อมูล, ค่า default, relation
- รหัสอ้างอิง identifier กฎห้ามซ้ำ ห้ามเปลี่ยน
- role, permission, ขอบเขตข้อมูลที่แต่ละคนเห็นได้
- validation, ช่วงค่า, ข้อความ error
- สูตรบัญชี, ภาษี, ต้นทุน, การปัดเศษ
- acceptance criteria

**ตัดสินใจเองได้ ไม่ถือว่าเดา** — พวกนี้เป็นเรื่องช่าง:
- ชื่อตัวแปร ชื่อฟังก์ชัน การจัดโครงสร้างไฟล์
- style การเขียนโค้ด การจัด format
- วิธีเขียน test ให้ครอบคลุมกรณีที่กำหนดไว้แล้ว
- การ refactor ที่ไม่เปลี่ยนพฤติกรรม

เส้นแบ่งคือ: **ถ้ากระทบกฎธุรกิจ สิทธิ์ ความถูกต้องของข้อมูล บัญชี ความปลอดภัย API/Event Contract หรือ Acceptance Criteria = ห้ามเดา** ส่วนความต่างด้านการนำเสนอหรือรายละเอียดภายในที่ย้อนกลับได้ง่าย ไม่เปลี่ยนข้อมูลถาวร และไม่กระทบความปลอดภัย จัดเป็นเรื่องที่ปรับภายหลังได้

## รูปแบบการถาม
แต่ละคำถามเขียนให้ครบ 6 ข้อนี้ ลุงจืดจะได้ตัดสินใจจบในรอบเดียว:
1. เรื่องอะไร / workflow ไหน
2. ตรงไหนไม่ชัด (ยกข้อความมาเลย)
3. ทำไมต้องรู้ก่อนถึงทำต่อได้
4. ถ้าเลือกผิดกระทบอะไร — ข้อมูล ผู้ใช้ บัญชี ความปลอดภัย ระบบอื่น
5. ตัวเลือกที่มี พร้อมข้อดีข้อเสีย
6. AI แนะนำข้อไหน เพราะอะไร

แล้วจัดคำถามเป็น 3 กอง:

| กอง | ความหมาย | AI ทำยังไงระหว่างรอ |
|---|---|---|
| **ต้องตัดสินใจก่อน** | ไม่รู้แล้วทำต่อไม่ได้ | หยุดส่วนนั้น |
| **ควรตัดสินใจ** | ทำต่อได้แต่เสี่ยงต้องรื้อ | ทำต่อ แต่แยกโค้ดส่วนนี้ให้รื้อง่าย |
| **ปรับภายหลังได้** | เป็นเรื่องการนำเสนอหรือรายละเอียดภายในที่ย้อนกลับง่าย ไม่เปลี่ยนข้อมูลถาวร Contract สิทธิ์ บัญชี หรือความปลอดภัย | ทำต่อได้ **แต่ต้องเขียนไว้ว่าใช้ค่าอะไร และทำ TODO ไว้ในโค้ด** |

กองที่ 3 สำคัญ: เดินหน้าได้ แต่ห้ามเงียบ ต้องบอกทุกครั้งว่าตัดสินใจอะไรไปเอง

## ใครแก้เอกสารได้

**ลุงจืดคนเดียว** สำหรับทุกไฟล์ใน `docs/` และไฟล์นี้ด้วย
AI อ่านได้อย่างเดียว ห้ามสร้าง ห้ามแก้ ห้ามเปลี่ยนชื่อ ห้ามย้าย ห้ามลบ ไม่มีข้อยกเว้น ไม่ว่าจะมั่นใจแค่ไหน ไม่ว่าจะเจอ typo ชัด ๆ
อยากแก้ → เขียนเป็นข้อเสนอในแชท ให้ลุงจืดก๊อปไปแก้เอง

---

## แนะนำได้ ไม่นับว่าเดา
สองอย่างนี้ต่างกัน:
- **เดา** = เขียนโค้ดหรือตอบไปเลยเหมือนรู้แล้ว ทั้งที่ไม่รู้
- **แนะนำ** = บอกว่า "ยังไม่มีกฎเรื่องนี้ ผมคิดว่าควรเป็นแบบ ก เพราะ..." แล้วรอคำตอบ
ข้อเสนอของ AI **ไม่ใช่กฎ** จนกว่าลุงจืดจะยืนยันและเขียนลงเอกสาร ห้ามอ้างข้อเสนอเก่าของตัวเองเป็นกฎในรอบถัดไป

## ก่อนเริ่มงานใหม่ ลุงจืดควรเขียนอะไรบ้าง
นี่คือรายการช่วยจำ ไม่ต้องเขียนครบทุกข้อ แต่ถ้าข้อที่เกี่ยวข้องกับงานยังไม่ชัด AI ต้องจัดเข้ากองตาม [รูปแบบการถาม](#รูปแบบการถาม) และหยุดเฉพาะส่วนที่ห้ามเดา ส่วนกอง "ปรับภายหลังได้" ทำต่อพร้อมแจ้งค่าที่เลือกและเขียน TODO
1. **เป้าหมาย** — ผู้ใช้ต้องทำอะไรได้ แก้ปัญหาอะไร
2. **ขอบเขต** — ระดับ Platform, Holding, Company, Branch หรือผู้ใช้คนไหน
3. **คำศัพท์** — คำธุรกิจแต่ละคำแปลว่าอะไร
4. **เจ้าของข้อมูล** — ข้อมูลหลักอยู่ไหน ใครสร้าง อ่าน แก้ ปิด ยกเลิกได้
5. **รหัสและตัวตน** — GUID, code, เลขเอกสาร, กฎห้ามซ้ำ ห้ามเปลี่ยน
6. **ข้อมูลเชิงธุรกิจ** — ต้องเก็บข้อมูลอะไร ข้อมูลใดบังคับ กฎความถูกต้อง และอายุข้อมูล ส่วนโครงสร้างจัดเก็บให้ยึด [ลำดับความน่าเชื่อถือของเอกสาร](#ลำดับความน่าเชื่อถือของเอกสาร)
7. **Workflow** — เริ่มยังไง มีขั้นตอนไหน เงื่อนไข สถานะ ทางแยก กรณีพัง จบยังไง
8. **สิทธิ์** — ใครทำขั้นตอนไหนได้ เห็นข้อมูลแค่ไหน
9. **Validation** — อะไรบังคับ รูปแบบไหน ช่วงค่าเท่าไหร่ ผิดแล้วขึ้นว่าอะไร
10. **Lifecycle** — create, activate, deactivate, soft delete, restore, cancel, reversal, เก็บประวัติ
11. **ตัวเลขและบัญชี** — currency, precision, scale, การปัดเศษ, ภาษี, ต้นทุน, วิธีตรวจยอด
12. **Event และ Integration** — ใครส่ง ใครรับ, idempotency, ลำดับ, retry, DLQ, ระบบข้างนอก
13. **หน้าจอ** — หน้าไหน ปุ่มอะไร ช่องอะไร ข้อความว่าอะไร ภาษา mobile accessibility
14. **ความปลอดภัยและ Audit** — ใครทำ เมื่อไหร่ tenant ไหน secret session อะไรที่ต้องตรวจย้อนหลังได้
15. **Error และ Recovery** — error code, rollback, retry, reconciliation, กู้คืนยังไง
16. **Acceptance Criteria** — Given/When/Then, ข้อมูลทดสอบ, role/tenant, edge case, หลักฐานว่าผ่าน
17. **ข้อจำกัดและเรื่องที่ยังไม่ตัดสิน** — อะไรที่ห้ามเดาเด็ดขาด งานไหนต้องรอ
