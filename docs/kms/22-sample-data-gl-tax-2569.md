## 3. ลำดับการทำงาน (`seed`)

1. `POST /api/auth/demo-login` → token (อยู่ในหน่วยความจำเท่านั้น ไม่พิมพ์/ไม่บันทึก) → `POST /api/workspace/select-holding` (`rungrueng`/`01`/`00000`) — `scripts/seed-gl-tax-rungrueng-2569.mjs:67-73`
2. **เลือกสมุดรายวันต่อ booktype ครั้งเดียว** (`:89-110`): manifest → สมุดประเภทนั้นที่มีใบของชุดนี้อยู่แล้ว (docno = รหัส + เลขของ scenario) → สมุดที่มีใบมากที่สุด (เสมอกันเรียงรหัส) — ไม่เลือกด้วยรหัสสมุด เพราะสมุดเป็น master ที่ผู้ใช้ตั้งเอง: **prod ใช้ `UV` = ขาย, `SV` = ซื้อ และมี `AR`/`AP` ประเภทเดียวกันด้วย** ส่วน local ใช้ `SV` = ขาย, `UV` = ซื้อ; ถ้าเลือกใหม่ต่างจากเดิม docno จะเปลี่ยนแล้วเกิดใบซ้ำ จึงบันทึก `books` ลง manifest
3. บัญชี: ต้องมีอยู่และเป็นบัญชีลงรายการได้ ไม่งั้นสร้างจากนิยาม (ต้องมีบัญชีพ่อก่อน) — ตรวจครบทั้งรายการแบบอ่านอย่างเดียวก่อนสร้างบัญชีแรก (ขาดบัญชี/บัญชีพ่อ = หยุดโดยยังไม่เขียนอะไร); รหัสบัญชีเป็นข้อมูลของผัง rungrueng ไม่ใช้เป็นเงื่อนไข (`:182-198`)
4. ใบรายวัน (`:113-141`, `:200-230`): ตรวจ เดบิต = เครดิต เป็นสตางค์ `BigInt`, VAT = 7% ของฐาน (ปัดครึ่งขึ้นต่อใบ), ภาษีหัก = อัตรา × ฐาน พอดี; docno มีแล้ว = ข้าม — ยกเว้นใบร่างของชุดนี้ที่ยังไม่ผ่านรายการ = ผ่านรายการต่อ (อยู่ใน manifest หรือเนื้อหาตรง scenario ทั้งหัวใบ บรรทัด VAT และภาษีหัก — `sameContent`) ไม่มี = `create` แล้ว `post`; ถ้ายังมีใบของชุดที่ไม่ผ่านรายการ (ใบร่างเนื้อหาไม่ตรง/กลับรายการแล้ว) และยังมีแบบยื่นที่ต้องบันทึก = หยุดพร้อมรายชื่อใบ ไม่บันทึกแบบยื่น (`:232-244`) เพราะ prefill อ่านเฉพาะใบที่ผ่านรายการและแบบที่บันทึกแล้วไม่ถูกเติมใหม่
5. ทะเบียนบริษัท (`:144-154`): `GET/PUT /backend/organization/company/01` (ทางเดียวกับ `frontend/src/app/system-settings/company-branch-tree-view.tsx:784,1072`) — ถ้า response ยังไม่มี `address` = backend รุ่นเก่า พิมพ์ `registry has no address fields yet` แล้วทำต่อ; มี `address` แต่ว่างทุกช่อง = PUT ทั้งก้อนเดิม + `address` + `phone` (ถ้าว่าง); มีค่าแล้ว = ไม่แตะ
6. แบบยื่น (`:157-174`, `:245-257`): ฉบับของแบบ+งวดมีแล้ว = ข้าม; ไม่มี = `prefill` → เติมช่องที่ schema ของแบบนั้นมีเท่านั้น (`POST /api/goapi/api/report/tax/form/schema`): ที่อยู่สำนักงานใหญ่ + โทรศัพท์ (ถ้าว่าง) เฉพาะเมื่อ prefill ให้ช่อง `addr_*` ว่างทุกช่อง — มีที่อยู่แล้วแม้บางช่อง = ไม่แตะทั้งที่อยู่และโทรศัพท์ (ไม่ผสมสองที่อยู่ กฎเดียวกับ `applyRegistryAddress` ใน `backend/internal/goapi/handlers/tax_form_fill.go`), `signer_name` นายวิชัย รุ่งเรืองกิจ, `signer_position` กรรมการผู้จัดการ, `tax_section = 3tres` ของ ภ.ง.ด.3/53, `media_ref_no` จาก env เท่านั้น → `save`

`verify` (`:273-317`, อ่านอย่างเดียว): ทะเบียนภาษีซื้อ/ขาย + รายงานภาษีหัก ณ ที่จ่ายจ่าย/รับ เดือน 7–9 (จำนวน ยอดฐาน ยอดภาษี), ไฟล์ยื่นด้วยสื่อ (`rdfile`) ของ ภ.ง.ด.2/3/53 ที่บันทึกไว้, PDF แบบทุกฉบับ, 50 ทวิ ของ scenario `pay:6908-0105`/`0106`/`0107` (หาใบจาก scenario key → สมุดใน manifest → id ใน manifest หรือรายการจริง) → `tmp/sample-data/out/<host>/` + `verify-report.json`


## 8. ข้อจำกัด

- ผูกกับผังบัญชีและสมุดรายวันของ `rungrueng` — holding อื่นที่ผังต่างกันจะหยุดตั้งแต่ขั้นบัญชี (บอกรหัสที่ขาด) โดยยังไม่เขียนอะไรลงระบบ (ตรวจครบทุกบัญชีก่อนสร้าง; `--apply` บันทึกแค่สมุดที่เลือกลง manifest ในเครื่องเมื่อผ่านขั้นบัญชี)
- ต้องเปิดปุ่ม Demo; ปิดแล้ว (ก่อน go-live ตาม `AGENTS.md`) สคริปต์ใช้ไม่ได้
- แบบยื่นบันทึกแค่ ก.ค./ส.ค. (ก.ย. ยังไม่ครบกำหนดยื่น ณ วันที่ seed); ไม่ยื่นจริง ไม่ส่ง e-Filing
- แบบที่มีอยู่แล้วจะไม่ถูกแก้ (เช่น หลังทะเบียนบริษัทมีที่อยู่ ฉบับเดิมยังเป็นหัวแบบเดิม) — ต้องแก้ในหน้าแบบยื่นเอง
- `seed` ไม่ใช้ requestid แบบกำหนดตายตัว: ถ้าหยุดกลางคันหลัง `create` ก่อนบันทึก manifest ใบนั้นเป็นใบร่าง — รอบถัดไปผ่านรายการให้เมื่อเนื้อหาตรง scenario; ใบร่างที่เนื้อหาไม่ตรง (มีคนแก้) หรือใบที่กลับรายการแล้ว สคริปต์ไม่แตะ และหยุดก่อนบันทึกแบบยื่นที่ยังขาด (บอกรายชื่อใบ) — ต้องแก้/ผ่านรายการเองในหน้าจอแล้วรันใหม่
- verify ไม่ได้เทียบยอดกับค่าคาดหวังอัตโนมัติ — อ่านยอดใน `verify-report.json` เทียบกับ §2/`.data.mjs`
