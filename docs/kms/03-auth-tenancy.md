# การยืนยันตัวตน เซสชัน และ Tenancy (Holding / Company / Branch)
> ตรวจล่าสุด: 2026-09-07 (commit d93a210d) — ผู้เขียน: AI reader; ทุกข้อเท็จจริงอ้าง path:line · ตรวจซ้ำโดย fact-checker

## 1. สรุปสั้น
- Access token ของระบบ **ไม่ใช่ JWT** แต่เป็น opaque SHA-256 ที่เก็บเป็น Redis hash (`auth-<token>`, `refresh-<token>`, `session-<uid>`) — `backend/pkg/microservice/auth.go:691-697`; JWT (`backend/pkg/microservice/jwt.go:28-58`) ใช้เฉพาะ binary รอง (`backend/cmd/app/main.go`, `backend/cmd/authenticationservice/main.go`, `backend/cmd/ws/main.go`) ไม่ใช่ `backend/main.go`
- อายุ: access ≤ 15 นาที, session idle/absolute 12 ชม. (`backend/pkg/microservice/auth.go:74-78`); `NewAuthService` ใน main ขอ 3 วัน/30 วัน แต่ถูก `boundedDuration` ตัดลง (`backend/main.go:264`, `backend/pkg/microservice/auth.go:88-89`)
- **Redis เป็นแค่ที่เก็บ "workspace ที่เลือก" — สิทธิ์จริงอ่านสดจาก MongoDB ทุก request** (`users`/`shopusers`/`shops`/`organizationcompanies`/`organizationbranches`) ผ่าน `liveAuthorization.Authorize` — `backend/pkg/microservice/live_authorization.go:106-208`; ถ้า `permissionversion`/role ใน Mongo ไม่ตรงกับ session → 403 "Workspace access changed." (`backend/pkg/microservice/auth.go:241-246`)
- Tenancy ผูกกับ token ฝั่ง server: client เรียก `POST /select-holding` แล้ว server จด `holdingcode/businesscode/branchuid/role` ลง hash ของ token+session (`backend/pkg/microservice/auth.go:731-772`) — request ปกติ**ไม่ส่ง holding ผ่าน header/cookie**; goapi เพียงตรวจว่า `holdingcode` ใน query/body (ถ้ามี) ตรงกับ token (`backend/internal/goapi/bootstrap.go:235-250`)
- ช่องทาง login ที่ LIVE ใน `main.go` มี 4 ทาง: `/login` (username+password), `/googlelogin`, `/demo-login`, `/dev-login` (สองทางหลังเปิดด้วย env) — `backend/internal/authentication/authentication_http.go:128-137`

## 6. Tenancy: holding → company → branch
- คำศัพท์ใน code: holding = collection `shops` (`backend/internal/shop/models/shop.go:9,104`), membership = `shopusers` (`backend/internal/authentication/models/user.go:399-401`), company = `organizationcompanies`, branch = `organizationbranches` (`backend/pkg/microservice/live_authorization.go:79,89`); `businesscode` = รหัสบริษัท (`code` ใน organizationcompanies) — `backend/pkg/microservice/live_authorization.go:163-166`
- `POST /select-holding` body `{holdingcode, businesscode?, branchuid?}` (`backend/internal/authentication/models/user.go:240-244`): handler normalize + ตรวจ company มีจริงและ active (`backend/internal/authentication/authentication_http.go:927-993`) → `AccessShop` ตรวจ membership active/ไม่หมดอายุ, ตรวจ `AccessScopes` ว่าอนุญาต company/branch (`backend/internal/authentication/services/authentication_service.go:804-882`) → `SelectShop` เขียน workspace ลง `auth-*` และ `session-*` (`backend/pkg/microservice/auth.go:731-772`)
- Role ใน membership: `0=USER, 1=ADMIN, 2=OWNER, 255=SYSTEM` (`backend/internal/authentication/models/user.go:246-254`); live authorization ปฏิเสธ role > 2 (`backend/pkg/microservice/live_authorization.go:127`); `AccessScope{scopetype: holding|company|branch, companyuid, branchuid, allbranches}` (`backend/internal/authentication/models/user.go:235-242`) — **ว่าง = ไม่ผ่าน** (fail closed) ยกเว้น OWNER/ADMIN ที่ไม่มี scope = ทั้งกลุ่มกิจการ
- **ขอบเขต "ใช้ได้ทั้งกลุ่มกิจการ" (`scopetype: holding`, ADR [decisions/2026-09-24-holding-wide-access-scope.md](decisions/2026-09-24-holding-wide-access-scope.md))**: เก็บเป็นกฎเดียว `[{"scopetype":"holding"}]` ไม่แตกเป็นรายบริษัทตอนบันทึก (`backend/internal/shop/scopes_postgres.go:42`) → ผู้อ่านขยายตอนอ่านเป็นทุกบริษัทที่ **active** รวมบริษัท/สาขาที่เพิ่มภายหลัง: `FindActiveMembership` (`backend/internal/organization/access/membership.go:99`) ป้อน live authorization + รายการ/รายละเอียดบริษัท-สาขา; `HasHoldingScope` + `ScopesAllowCompanySelection/BranchSelection` (`backend/internal/authentication/models/user.go:277,291,321`) ให้ `AccessShop` และ GL `sessionScopeAllowed` (`backend/internal/generalledger/httpapi/scope.go:96`) ผ่านเมื่อผู้เรียกตรวจแล้วว่าบริษัท/สาขา active (`ResolveCompanyUID` ตรวจ `is_active`); ขอบเขตไม่ให้สิทธิ์หน้าจอ/GL เพิ่ม (`role_permissions` แยกเหมือนเดิม)
- บันทึกขอบเขต (`PUT /holding/permission`): ทุกกฎต้องเป็น holding/company/branch และบริษัท/สาขาต้องอยู่ใน holding นี้ ไม่งั้น 400 `VALIDATION_FAILED` (`ss_err_access_scope_invalid`); ADMIN ให้สิทธิ์เกินขอบเขตตัวเองไม่ได้ — ทั้งกลุ่มกิจการให้ได้เฉพาะ OWNER หรือ ADMIN ที่เป็นทั้งกลุ่มกิจการ ไม่งั้น 403 `FORBIDDEN` (`ss_err_access_scope_exceeds_grantor`, `checkScopeGrant` `backend/internal/shop/shopuser_service.go:385`) และแก้/ลบสมาชิกที่บทบาท+ขอบเขตปัจจุบันเกินตัวเองไม่ได้ (`checkTargetWithinGrantor` :374; สมาชิกเป้าหมายหาจาก editusername → username → useruid ที่ `findSaveTarget` :354); BFF ปฏิเสธกฎขอบเขตที่ผิดแม้กฎเดียวด้วย 400 `ss_err_access_scope_invalid` (ไม่ทิ้งเงียบ ๆ); repo validation (ไม่มี username, useruid ไม่ใช่ uuid) = 400 `VALIDATION_FAILED` ไม่ใช่ 500 (`errMemberRequestInvalid`); จอแก้ไขและรายการสมาชิกอ่าน OWNER/ADMIN ที่ไม่มี scope เป็น `[{"scopetype":"holding"}]` เหมือนกัน (`scanMember` `backend/internal/shop/shopuser_postgres_repository.go:104`)
- การเปลี่ยนสถานะ company/branch/holding ทำใน Mongo transaction เดียว: อัปเดต `isactive`+`__v`, `$inc permissionversion` ของสมาชิกที่เกี่ยว, เขียน `organizationaudits` + `outboxevents` → session เก่าจะโดน 403 ทันทีในคำขอถัดไป (`backend/internal/organization/status_change.go:81-163`)

## 8. Guard ระดับ handler ที่พบ
- แก้ holding (`PUT /holding/:id`) ต้องเป็น OWNER/ADMIN active (`backend/internal/shop/shop_http.go:520-528`); สร้าง holding ต้อง `RequireEmailedAccount` (`backend/internal/shop/shop_http.go:132-138`)
- บันทึก/ลบสิทธิ์สมาชิก (`/holding/permission`) เช็ค `userInfo.Role` เป็น OWNER/ADMIN จาก session; `SaveFullProfile` (`backend/internal/shop/shopuser_postgres_repository.go:243`) แยก **เพิ่ม** กับ **แก้** ด้วย `editusername`/`useruid` (มี = แก้): เพิ่มคนที่เป็นสมาชิกอยู่แล้ว = 409 `ss_err_user_already_member`, รหัสผู้ใช้ชนบัญชีของคนอื่น = 409 `ss_err_user_code_taken` เว้นแต่ส่ง `addexistinguser: true` และตรงบัญชีเดียว (ผูกบัญชีเดิมโดยไม่แตะรหัสผ่าน), เปลี่ยนรหัสผู้ใช้/อีเมลของบัญชีที่เจ้าของ login แล้วหรือใช้ร่วม holding อื่น = 409 `ss_err_user_code_locked`/`ss_err_user_email_locked`, แก้สมาชิกที่ถูกลบแล้ว = 404 — ไม่มีการทับข้อมูลเงียบ ๆ แล้ว (error map `backend/internal/shop/shopuser_http.go:265-269`)
- วันหมดอายุการเข้าใช้งาน `holding_members.access_expiry_date` (DATE) = **วันสุดท้ายที่ใช้งานได้ (นับรวมวันนั้น)** — จอใช้ป้าย "ใช้งานได้ถึงวันที่"; ปิดสิทธิ์ 00:00 ของ **วันถัดไป** ตาม timezone ของ holding (ค่าเริ่มต้น Asia/Bangkok) กฎเดียวที่ `authmodels.AccessEndsAt`/`AccessExpired` (`backend/internal/authentication/models/access_expiry.go:34`, `:42`; `centraldb.AccessExpiryInstant` `backend/internal/centraldb/centraldb.go:253` ห่อไว้); ตรวจ **ทุกทางที่อ่านสมาชิกภาพ** → 403 `user_access_expired`: เลือก holding/บริษัท (`AccessShop`), `FindActiveMembership` (`backend/internal/organization/access/membership.go:66` — รวม `FindActiveHoldingManager` ที่ MCP/API token ใช้ทั้งตอนออกและทุกครั้งที่ใช้), `rolepermission` (`postgresMemberRole`), GL (`resolveScope` `backend/internal/generalledger/httpapi/scope.go:56`), 50 ทวิ; ผู้สร้าง holding ตั้งวันหมดอายุไม่ได้ (409 `ss_err_creator_access_expiry`)
- เพิ่มผู้ใช้ที่เคย **ถูกลบออกจากกลุ่มนี้** กลับได้ (ผูกบัญชีเดิม) — การลบสมาชิกบันทึก `member_removed` ใน `organization_audits` (append-only: ผู้ลบ + สถานะก่อนลบ) และ `SaveFullProfile` ใช้ร่องรอยนี้แยกจากบัญชีของคนอื่น (`backend/internal/shop/shopuser_postgres_repository.go:146`, `Delete` :450); บัญชีที่ใช้งานอยู่ในกลุ่มอื่นยังได้ 409; จอ "บัญชีเข้าระบบ" เมื่อได้ `ss_err_user_code_taken` ขึ้น dialog ยืนยันก่อนส่งซ้ำพร้อม `addexistinguser: true` (ยกเลิก = บอกให้เปลี่ยนรหัสผู้ใช้)
- ชุดสิทธิ์ (`role_permissions`) มี `version` — แก้บนข้อมูลเก่าได้ 409 `ss_err_permission_set_changed` (field `__v`, `backend/internal/organization/rolepermission/permission_set_rows.go:215`); ประเภทธุรกิจ (`business_types`) อ่านได้เมื่อเป็นสมาชิก เขียนได้เฉพาะ OWNER/ADMIN
- `/holding-member/list` รับ `holdingcode` จาก query แล้วให้ service ตรวจ role ต่อ holding เอง (จึงใช้ได้ก่อนเลือก holding) (`backend/internal/shop/shopuser_http.go:152-175`; `backend/internal/shop/shopuser_service.go:421-424`) — อ่านอย่างเดียว: เพิ่ม/ถอดสมาชิกทำที่ ตั้งค่าระบบและการเข้าถึง › บัญชีเข้าระบบ (`/holding/permission`) ตามที่ลุงจืดเลือก 2026-09-23
