> MongoDB, Redis, Kafka และ ClickHouse ถูกถอดออกจากระบบเมื่อ 2026-09-23 ([decisions/2026-09-23-remove-mongo-kafka-redis-clickhouse.md](decisions/2026-09-23-remove-mongo-kafka-redis-clickhouse.md)) — ทุกอย่างในบทความนี้อยู่บน PostgreSQL; **ห้ามเพิ่มระบบเหล่านี้กลับเข้ามา**

## 1. สรุปสั้น
- Access token ไม่ใช่ JWT — เป็น opaque SHA-256 ของ ksuid (`NewUUID()` `backend/pkg/microservice/util.go:59` แฮชที่ `backend/pkg/microservice/auth.go:691-692`) เก็บเป็น key/hash ใน **ตาราง `cache_entries`** ของฐานกลาง `bcai_projection` ผ่าน interface `ICacher` (`backend/pkg/microservice/cacher.go:18-42`) — prefix: `auth-<token>`, `refresh-<token>`, `session-<uid>`, `xapikey-<token>`, `session-revoked-<uid>`, `refresh-used-<refresh>` (`backend/pkg/microservice/auth.go:95-101`)
- `JwtService` (`backend/pkg/microservice/jwt.go:28-37`) ไม่มีผู้เรียกในโค้ดที่รันจริง (มีแค่ `backend/pkg/microservice/jwt_test.go`) — `backend/cmd/` เหลือแค่ `cmd/glseed/`
- อายุ token: access ≤ 15 นาที, session idle/absolute 12 ชม. (`backend/pkg/microservice/auth.go:74-78`); `backend/main.go:118` ขอ 3 วัน/30 วัน แต่ถูก `boundedDuration` ตัดลง (`backend/pkg/microservice/auth.go:88-89,153`)
- **สิทธิ์จริงอ่านสดจาก PostgreSQL ทุก request** ผ่าน `liveAuthorization.Authorize` (`backend/pkg/microservice/live_authorization.go:46-121`): `users` (:55) → `FindActiveMembership` (`holding_members` JOIN `users`+`holdings`, `backend/internal/organization/access/membership.go:66-123`) → `companies` (:91) → `branches` (:111); role ใน `UserInfo` ถูกแทนด้วย role สดจากฐาน (:80)
  - สมาชิกภาพ/holding/บริษัท/สาขาไม่ active หรือหมดอายุ → `ErrLiveWorkspaceAccess` → ล้าง workspace ใน session แล้วตอบ 403 "Workspace access changed." (path ใน `exceptShopPaths` ผ่านแบบ login-only) — `backend/pkg/microservice/auth.go:949-958,242-245`
  - ผู้ใช้ไม่ active → `ErrLiveUserAccess` → revoke session แล้วตอบ 401 "Session expired." (`backend/pkg/microservice/auth.go:960-963,246-247`)
- Tenancy ผูกกับ token ฝั่ง server: client เรียก `POST /select-holding` แล้ว server จด `holdingcode/businesscode/branchuid/role` ลง `auth-*`/`session-*` (`backend/pkg/microservice/auth.go:731-772`) — request ปกติไม่ส่ง holding ผ่าน header/cookie
- ช่องทาง login ที่ LIVE มี 4 ทาง: `/login`, `/googlelogin`, `/demo-login`, `/dev-login` (สองทางหลัง register เฉพาะเมื่อเปิดด้วย env) — `backend/internal/authentication/authentication_http.go:126-166`

## 6. Tenancy: holding → company → branch
- คำศัพท์ใน code: holding = ตาราง `holdings` (`backend/internal/shop/shop_postgres_repository.go:48,60,68,94`), membership = `holding_members` (`backend/internal/organization/access/membership.go:85`), company = `companies`, branch = `branches` (`backend/pkg/microservice/live_authorization.go:91,111`); `businesscode` = คอลัมน์ `code` ใน `companies`
- `POST /select-holding` body `{holdingcode, businesscode?, branchuid?}`: handler normalize + ตรวจบริษัทมีจริงและ active (`backend/internal/authentication/authentication_http.go:961`) → `AccessShop` ตรวจ membership active/ไม่หมดอายุ + `AccessScopes` อนุญาต company/branch (`backend/internal/authentication/services/authentication_service.go:812-882`) → `SelectShop` เขียน workspace ลง `auth-*`/`session-*` (`backend/pkg/microservice/auth.go:731-772`)
- Role ใน membership: `0=USER, 1=ADMIN, 2=OWNER, 255=SYSTEM` (`backend/internal/authentication/models/user.go:214-218`); live authorization ปฏิเสธ role > OWNER (`backend/pkg/microservice/live_authorization.go:74`); `AccessScope{scopetype: holding|company|branch, companyuid, branchuid, allbranches}` (`backend/internal/authentication/models/user.go:236-243`) — **ว่าง = ไม่ผ่าน** (fail closed) ยกเว้น OWNER/ADMIN ที่ไม่มี scope = ทุกบริษัท active ในกลุ่ม (`backend/internal/organization/access/membership.go:115-120`)
- **ขอบเขต "ใช้ได้ทั้งกลุ่มกิจการ" (`scopetype: holding`, ADR [decisions/2026-09-24-holding-wide-access-scope.md](decisions/2026-09-24-holding-wide-access-scope.md))**: เก็บเป็นกฎเดียว `[{"scopetype":"holding"}]` (`backend/internal/shop/scopes_postgres.go:48`) → ผู้อ่านขยายตอนอ่านเป็นทุกบริษัทที่ active: `FindActiveMembership`/`FindActiveHoldingManager` (`backend/internal/organization/access/membership.go:66,142`) ป้อน live authorization + รายการ/รายละเอียดบริษัท-สาขา; `HasHoldingScope` + `ScopesAllowCompanySelection/BranchSelection` (`backend/internal/authentication/models/user.go:278,292,322`) ให้ `AccessShop` และ GL `sessionScopeAllowed` (`backend/internal/generalledger/httpapi/scope.go:103`) ผ่านเมื่อบริษัท/สาขา active
- บันทึกขอบเขต (`PUT /holding/permission`): ทุกกฎต้องเป็น holding/company/branch และบริษัท/สาขาต้องอยู่ใน holding นี้ ไม่งั้น 400 `VALIDATION_FAILED` (`ss_err_access_scope_invalid`); ADMIN ให้สิทธิ์เกินขอบเขตตัวเองไม่ได้ (403 `FORBIDDEN`/`ss_err_access_scope_exceeds_grantor`, `checkScopeGrant` `backend/internal/shop/shopuser_service.go:407`) และแก้/ลบสมาชิกที่บทบาท+ขอบเขตปัจจุบันเกินตัวเองไม่ได้ (`checkTargetWithinGrantor` :396; สมาชิกเป้าหมายหาจาก `findSaveTarget` :376)
- การเปลี่ยนสถานะ company/branch/holding ทำใน `sql.Tx` เดียว: อัปเดต `is_active`+`version`, เขียน `organization_audits` (`backend/internal/organization/audit.go:40,57`) → session เก่าโดน 403 ในคำขอถัดไปเพราะ live authorization อ่านสด
- สร้าง holding: ผู้สร้างต้องมี Google identity ที่ active (บัญชี demo ยกเว้นผ่าน `demo.IsDemoUser`) — `RequireEmailedAccount` (`backend/internal/organization/creator_access.go:27,67`); transaction เขียน `holdings` + membership OWNER + audit `holding.created` (`backend/internal/shop/shop_service.go:79`); สร้าง company/branch ต้องเป็น OWNER/ADMIN ของ holding ที่เลือก (`RequireHoldingAdmin`, `backend/internal/organization/creator_access.go:32-96`)
- สิทธิ์ใช้งานหน้าจอ: `GET /organization/role-permission/me` = union ของชุด built-in ตาม role + `permissionsets` ที่สมาชิกเลือก จากตาราง `role_permissions` (`backend/internal/organization/rolepermission/role_permission_http.go:37,210-273`)
- เพิ่มผู้ใช้ที่เคย **ถูกลบออกจากกลุ่มนี้** กลับได้ (ผูกบัญชีเดิม) — การลบสมาชิกบันทึก `member_removed` ใน `organization_audits` (append-only) และ `SaveFullProfile` ใช้ร่องรอยนี้แยกจากบัญชีของคนอื่น (`backend/internal/shop/shopuser_postgres_repository.go:151-168,455-472`)
- ชุดสิทธิ์ (`role_permissions`) มี `version` — แก้บนข้อมูลเก่าได้ 409 `ss_err_permission_set_changed` (`backend/internal/organization/rolepermission/permission_set_rows.go:215`); ต้องส่ง `__v` ทั้งตอนแก้และลบ (`backend/internal/organization/rolepermission/role_permission_http.go:462-471,484-487`)
- วันหมดอายุการเข้าใช้งาน `holding_members.access_expiry_date` (DATE) = **วันสุดท้ายที่ใช้งานได้ (นับรวมวันนั้น)** — ปิดสิทธิ์ 00:00 ของวันถัดไปตาม timezone ของ holding (ค่าเริ่มต้น Asia/Bangkok) กฎเดียวที่ `authmodels.AccessEndsAt`/`AccessExpired` (`backend/internal/authentication/models/access_expiry.go:10,34,42`) ห่อโดย `centraldb.AccessExpiryInstant` (`backend/internal/centraldb/centraldb.go:269`); ตรวจทุกทางที่อ่านสมาชิกภาพ → 403 `user_access_expired` (`backend/internal/organization/access_expired.go:14,20`); ผู้สร้าง holding ตั้งวันหมดอายุไม่ได้ (409 `ss_err_creator_access_expiry`, `backend/internal/shop/shopuser_http.go:299`)
- `/holding-member/list` รับ `holdingcode` จาก query แล้วให้ service ตรวจ role ต่อ holding เอง (จึงใช้ได้ก่อนเลือก holding) — อ่านอย่างเดียว: เพิ่ม/ถอดสมาชิกทำที่ "ตั้งค่าระบบและการเข้าถึง › บัญชีเข้าระบบ" (`/holding/permission`) ตามที่ลุงจืดเลือก 2026-09-23 (`backend/internal/shop/shopuser_http.go:58,146-175`; `backend/internal/shop/shopuser_service.go:505`)

## 8. Guard ระดับ handler ที่พบ
- แก้ holding (`PUT /holding/:id`) ต้องเป็น OWNER/ADMIN ที่ active (`FindActiveHoldingManager`, `backend/internal/shop/shop_http.go:123`) และเปลี่ยนสถานะ active ได้เฉพาะ OWNER (:144-146); สร้าง holding (`POST /holding`) ต้อง `RequireEmailedAccount` (:80)
- บันทึก/ลบสิทธิ์สมาชิก (`/holding/permission`) เช็ค `userInfo.Role` เป็น OWNER/ADMIN (`backend/internal/shop/shopuser_http.go:188,384`) — role นี้มาจาก live authorization จึงเป็นค่าสดจากฐาน (§1); `SaveFullProfile` (`backend/internal/shop/shopuser_postgres_repository.go:253`) แยก **เพิ่ม** กับ **แก้** ด้วย `editusername`/`useruid`: เพิ่มคนที่เป็นสมาชิกอยู่แล้ว = 409 `ss_err_user_already_member`, รหัสผู้ใช้ชนบัญชีของคนอื่น = 409 `ss_err_user_code_taken` เว้นแต่ส่ง `addexistinguser: true`, เปลี่ยนรหัสผู้ใช้/อีเมลของบัญชีที่ล็อกอยู่ = 409 `ss_err_user_code_locked`/`ss_err_user_email_locked`, แก้สมาชิกที่หาไม่พบ/ถูกลบแล้ว = 404 `ss_err_not_found` — error map ที่ `backend/internal/shop/shopuser_http.go:294-301`
- ประเภทธุรกิจ (`business_types`) อ่านได้เมื่อเป็นสมาชิก เขียนได้เฉพาะ OWNER/ADMIN
