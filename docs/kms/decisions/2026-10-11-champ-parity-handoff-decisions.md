# การตัดสินใจ 4 ข้อ ต่อจาก handoff Champ full parity (2026-10-11)

## ที่มา
ระหว่างทำต่อ [`docs/handoff/HANDOFF-2026-10-11-CHAMP-FULL-PARITY-CRUD.md`](../../handoff/HANDOFF-2026-10-11-CHAMP-FULL-PARITY-CRUD.md) การตรวจโค้ดจริงพบว่าหลายจอที่เมนูแสดงว่า "เชื่อมแล้ว" เป็นหน้าจอที่มีแต่ UI (ข้อมูลฝังในโค้ด ไม่มี API/PostgreSQL) และมีเรื่องที่ต้องให้ลุงจืดเลือกทาง ลุงจืดเลือก 2026-10-11 (ตัวเลือกที่แนะนำทั้ง 4 ข้อ) และกำกับลำดับงานไว้ว่า *"ตอนนี้เอาระบบบัญชี และอื่นๆ ก่อน เทคนิคยัง"*

## Decision
1. **จอที่เป็นแค่ UI (~25 จอ)** เช่น จองสินค้า, ใบส่งของ, เตรียมจ่ายเจ้าหนี้, เตรียมเช็ค/เคลื่อนไหวเช็ค, บริการธนาคาร, ล็อกรายการ, hand-held → ขึ้นสถานะ "รอพัฒนา" ก่อน แล้วค่อยทำ backend จริงทีละจอ ห้ามขึ้น "เชื่อมแล้ว" ถ้ายังไม่มี API + บันทึก/อ่าน PostgreSQL จริง
2. **ยกเลิกเอกสาร ERP = ทั้งใบ** (header-level + เหตุผลพิมพ์เอง, Tier A ที่มีอยู่) ส่วนการยกเลิกรายบรรทัดแบบ Champ (Tier B) เลื่อนไปก่อน
3. **รายงาน** = เมนูมีชื่อรายงานครบตาม Champ แต่ทุกเมนูเปิดจอรายงานกลางจอเดียว ข้อมูลมาจาก report registry ฝั่ง backend (ตัวกรอง/เรียง/ยอดรวม/ส่งออก ตามนิยามของแต่ละรายงาน) ไม่สร้างจอใหม่ต่อรายงาน
4. **ข้อมูลหลักสินค้า** (สินค้า/หน่วย/กลุ่ม/ยี่ห้อ/คลัง/ราคา/ชุด) บน PostgreSQL ทำ **หลัง** งานบัญชี ลำดับงานบัญชี: ล็อกงวด → อายุหนี้ → ทะเบียนเช็ค → เตรียมจ่าย → มิติ (หน่วยงาน/ฝ่าย)

## Consequences
- เมนูจะมีจอ "รอพัฒนา" เพิ่มขึ้นชั่วคราว แต่ผู้ใช้ไม่ถูกหลอกด้วยข้อมูลปลอม และตรงกฎ backend-first / i18n
- ยกเลิกรายบรรทัดยังทำไม่ได้: ถ้าต้องแก้บางบรรทัดให้ยกเลิกทั้งใบแล้วออกใบใหม่
- report registry เป็นงานโครงสร้างครั้งเดียว รายงานถัดไปเพิ่มเป็นนิยามใน backend
- งานเทคนิค (PKCS#7/HSM/API gateway) ยังพักไว้
- ลำดับงานบันทึกใน memory `champ-parity-decisions-2026-10-11` และ memory-hub Ff9a6e0cf

## Decision รอบ 2 (2026-10-11) — ลุงจืดเลือก "ทำตาม Champ" ทั้ง 4 ข้อ
ตัวเลือกที่ผมเสนอให้เบี่ยงจาก Champ เพื่อ "กันยอดเพี้ยน" ถูกปฏิเสธทั้งหมด ความถูกต้องของยอดให้ได้จากการ derive/recalculate + audit event แทนการล็อก
1. **เช็ค D1** ทำวงจรเช็คครบแบบ Champ เป็นขั้น (CB-1→CB-6 ก่อน แล้วค่อยส่วนที่เหลือ) แม้ `mydocs/specs/gl/ar-ap-bank-design-notes.md:49` เขียนว่า workflow เช็คเป็นของระบบต้นทาง — [`cheque-bank.md`](../champ/design-2026-10-11/cheque-bank.md) §7
2. **เช็ค D8** เช็คที่ถูกอ้างแล้ว: ถามยืนยันแล้วแก้ฟิลด์หลักได้ และแก้สถานะในจอทะเบียนได้ ตาม Champ (`cqfrmcheqin.cpp:320-336`); ทุกการแก้บันทึก event — `cheque-bank.md` §4.3 ข้อ 7-8
3. **เตรียมจ่าย D11** ใบที่จ่ายไปบางส่วนแก้ได้จนจ่ายครบ แต่ห้ามลดยอดบรรทัดต่ำกว่าที่จ่ายไปแล้ว — [`ap-payment-prepare.md`](../champ/design-2026-10-11/ap-payment-prepare.md) §7
4. **รายงาน Q2** รายงานลูกหนี้/เจ้าหนี้ในจอรายงานกลางนับทุกใบที่บันทึกแล้วและไม่ยกเลิก ไม่ดูสถานะผ่านบัญชี (`APRepAgingDlg.cpp:188-214`) — [`report-registry.md`](../champ/design-2026-10-11/report-registry.md) Q2

ผลที่ตามมา: ยอดในรายงานหนี้อาจต่างจากบัญชีคุมได้เท่ากับเอกสารที่ยังไม่ผ่านบัญชี; ทะเบียนเช็คต้องมี event `edit`/`manual_status` และ recalculate ยอดคงเหลือทุกครั้งที่แก้
