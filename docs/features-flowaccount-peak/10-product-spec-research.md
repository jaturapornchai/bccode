# ผลค้นสเปกเพิ่มเติม — FlowAccount + PEAK Account

ตรวจเมื่อ 2026-09-07 | งานธุรกิจ บัญชี ภาษี การเงิน สินค้า และสินทรัพย์ ไม่รวมระบบเงินเดือน/HR

> เอกสารนี้เก็บผลค้นสเปกรอบก่อนหน้า (268 รายการ / 65 แหล่ง) รอบไล่เมนูต่อมาอัปเดตบัญชีรวมเป็น 306 รายการ / 113 แหล่ง ดู[09](09-flowaccount-peak-menu-catalog.md), [ผัง FlowAccount](11-flowaccount-menu-map.md) และ[ผัง PEAK](12-peak-account-menu-map.md) ตัวเลขในผลรอบเดิมด้านล่างคงไว้ตามขอบเขตการค้นครั้งนั้น

## 1. ผลตรวจและวิธีใช้

**ควรเพิ่มรายละเอียดในเอกสารเดิม** รอบนี้เพิ่มความสามารถ 25 รายการ และขยาย/แก้หลักฐาน 14 รายการเดิม บัญชีเมนูจึงเพิ่มจาก 243 เป็น **268 รายการใน 18 หมวด** อ้างอิงแหล่งทางการจากเดิม 35 เป็น **65 หน้า** รายการเหล่านี้รวมงานย่อย รายงาน ตั้งค่า และช่องทาง ไม่ใช่จำนวนหน้าจอไม่ซ้ำ

เป้าหมายคือทำให้การเทียบผลิตภัณฑ์ครบและตรวจสอบได้ ใช้[09 — บัญชีเมนู](09-flowaccount-peak-menu-catalog.md) ดูรายการรวม ใช้[03 — ตารางเปรียบเทียบ](03-comparative-matrix.md) ดูหลักฐานแยกค่าย และใช้เอกสารนี้ดูสิ่งที่เพิ่งค้นพบพร้อมข้อจำกัด

ตรวจจากแหล่งหลายประเภท: คู่มือใช้งานรายเรื่อง, หน้าฟีเจอร์ผลิตภัณฑ์, เอกสารนักพัฒนา/OpenAPI, และประกาศอัปเดตผลิตภัณฑ์ปี 2026 ข้อความการตลาดหรือบทความบัญชีทั่วไปไม่เพียงพอสำหรับรับรองปุ่ม เมนู หรือผลลงบัญชี ประกาศที่กล่าวถึงงานนอกขอบเขตถูกใช้เฉพาะส่วนงานธุรกิจที่เกี่ยวข้อง

ยังไม่ได้ล็อกอิน ทดสอบ API หรือทดสอบผลลงบัญชีจริง แพ็กเกจที่ระบุด้านล่างเป็นเงื่อนไขจากหน้าที่อ้างอิง ณ วันที่ตรวจ ไม่รับรองสิทธิ์ของบัญชีใดโดยไม่ตรวจบัญชีนั้น

## 4. Workflow และเงื่อนไขที่ควรเก็บในสเปกเทียบผลิตภัณฑ์

### 4.1 PEAK SMART Key และคลังเอกสาร

ลำดับงาน: อัปโหลด/รับไฟล์ → อ่านข้อมูล → ตรวจคู่ค้าและความเป็นเจ้าของเอกสาร → ตรวจผังบัญชี/ภาษี/รายการ → ใช้ข้อมูลหรือส่งผู้อนุมัติที่เลือก คู่มือยืนยันทั้งตัวช่วยข้อมูลและขั้นตอนตรวจ ไม่ควรอธิบายเพียง “มี OCR” [P30]

ตัวอย่างใช้งาน: รับใบกำกับภาษีซื้อที่มีเอกสารรายจ่ายอยู่แล้ว ให้ SMART Key อ่านเลขเอกสารและเลือกเชื่อมรายการที่ยังรอลงทะเบียนใบกำกับ ไม่ควรนับเป็นการสร้างรายจ่ายใหม่ทุกครั้ง ประกาศ 05/08/2026 ระบุ e-Document ขึ้นไป [P34]

เงื่อนไขที่ต้องแยก: ประกาศ 01/04/2026 ระบุ OCR PDF ไม่เกิน 5 หน้าและ Basic ขึ้นไป ขณะที่งานสร้าง/ตรวจเอกสารบางส่วนระบุ e-Document ขึ้นไป จึงต้องแยกสิทธิ์อ่านไฟล์ออกจากสิทธิ์งานปลายทาง ไม่สรุปว่า Basic ได้ทุกความสามารถของ SMART Key [P30], [P37]

### 4.2 นำเข้าผู้ติดต่อกับยอดหนี้ตั้งต้น

FlowAccount: ผู้ติดต่อ → นำเข้า → จับคู่คอลัมน์ → ตรวจซ้ำ/แก้ข้อมูล → ยืนยัน → ตรวจประวัติและผลนำเข้า รองรับ xlsx/xls/csv ไม่เกิน 5 MB และ 500 รายชื่อต่อไฟล์, Standard ขึ้นไปและสิทธิ์สร้าง/แก้ผู้ติดต่อ คู่มือระบุลบชุดนำเข้าได้ แต่ไม่ได้ยืนยันการย้อนผลเอกสารบัญชีที่ถูกใช้งานภายหลัง [F22]

PEAK: ลูกหนี้ตั้งต้นและเจ้าหนี้ตั้งต้นมี workflow รายเอกสาร เพื่อรับ/จ่ายต่อและติดตามเช็คที่ยังไม่ผ่านธนาคาร ต้องแยกจากทะเบียนคู่ค้าและยอดสรุปงบทดลอง [P26], [P27]

ตัวอย่างเปรียบเทียบ: นำเข้ารายชื่อผู้ติดต่อสำเร็จยังไม่ใช่หลักฐานว่ายอดหนี้เก่าถูกนำเข้าด้วย คู่มือ FlowAccount ระบุชัดว่างานนำเข้าผู้ติดต่อไม่กระทบยอดลูกหนี้/เจ้าหนี้ [F22]

### 4.3 ขอใบกำกับภาษีภายหลังและประวัติส่งเอกสาร

PEAK: เปิดลิงก์ในตั้งค่าเอกสาร → เลือกผู้ติดต่อขายปลีกที่ใช้กับรายการต้นทาง → ลูกค้ากรอกข้อมูล → ระบบออกเอกสารแทนใบกำกับอย่างย่อและส่งอีเมล เงื่อนไขเลือกผู้ติดต่อได้สูงสุด 5 รายชื่อทำให้ต้องตรวจรายการต้นทางด้วย ไม่ใช่ทุกบิลเข้าลิงก์ได้โดยอัตโนมัติ [P28]

ข้อมูลประวัติแสดงผู้ส่ง อีเมลปลายทาง และเวลา ซึ่งใช้ตรวจว่าเคยส่งจากระบบ แต่ยังไม่ใช่หลักฐานว่าลูกค้าเปิดอ่าน [P25]

### 4.4 หน่วยสินค้า สินค้าชุด และต้นทุน

FlowAccount Product API แยกสินค้าหลักกับรายการหน่วย รองรับอัตราแปลง บาร์โค้ดและราคาระดับหน่วย สเปกจึงควรตรวจทั้งรหัสสินค้าหลักและหน่วยที่เลือก ไม่รวม “บริการ”, “สินค้าไม่นับสต็อก” และ “สินค้านับสต็อก” เป็นชนิดเดียว [F19]

PEAK Product Sets เป็นการรวมสินค้า/บริการเพื่อเลือกลงเอกสารฝั่งรายรับ และประกาศระบุสร้างชุดทีละชุดในโปรแกรม PRO Plus ขึ้นไป ไม่ใช่หลักฐาน BOM หรือการผลิต [P32]

พบ FIFO ในคู่มือสินค้าของ FlowAccount และใบเบิกของ PEAK แต่ข้อความ “แสดงต้นทุนเฉลี่ย” ในหน้า Classic/New ของ FlowAccount ยังไม่ยืนยันว่าผู้ใช้เปลี่ยนวิธีลงบัญชีเป็น Average ได้ ต้องแยกวิธีคำนวณออกจากตัวเลขเฉลี่ยที่แสดงในรายงาน [F24], [F25], [P31]

### 4.5 มือถือและการอนุมัติ

FlowAccount MobilePOS ยืนยันการแนบภาพรับชำระและพิมพ์ใบเสร็จผ่านเครื่องเทอร์มัล Bluetooth/Wifi ควรตรวจรุ่นเครื่อง อุปกรณ์ และชนิดเอกสารที่พิมพ์จริงก่อนรับรองการใช้งานหน้าร้าน [F23]

PEAK Mobile อัปเดต 02/09/2026 เพิ่มเอกสารธุรกิจที่อนุมัติ/ปฏิเสธได้ รวมแบบทีละใบและหลายใบ เช่น ลดหนี้ เพิ่มหนี้ วางบิล และรับ/จ่ายมัดจำ โดยประกาศระบุ e-Document ขึ้นไป [P36]

## 5. สเปก API ที่ควรเพิ่มรายละเอียด

ข้อกำหนดต่อไปนี้เป็นสัญญาการเชื่อมต่อสาธารณะของผู้ให้บริการ ไม่ใช้อนุมานระบบจัดเก็บหรือสถาปัตยกรรมภายใน

### 5.1 FlowAccount: การเชื่อมต่อและเอกสาร

| หัวข้อ | สิ่งที่ยืนยันได้ | ผลต่อการเทียบสเปก |
|---|---|---|
| สิทธิ์เชื่อมต่อ | Client Credentials สำหรับ client ที่ผูกกิจการ และ OpenID สำหรับ partner ที่ให้ผู้ใช้อนุญาตเชื่อมหลายกิจการ [F17] | แยกการเชื่อมกิจการตนเองจากบริการที่เชื่อมหลายกิจการ |
| สภาพแวดล้อม | มี Sandbox และ Production แยกกัน; คู่มือระบุทดลอง Sandbox 30 วัน [F17] | ผลทดลองไม่ยืนยันสิทธิ์ Production |
| รูปแบบเอกสาร | Simple กับ Inline แยกกัน ส่วนลด/VAT มีเงื่อนไขตามประเภทกิจการ [F18] | ต้องตรวจ payload ตามรูปแบบเอกสารจริง |
| ความละเอียดตัวเลข | คู่มือระบุราคาต่อหน่วยและจำนวน 4 ตำแหน่ง; ยอดบรรทัดและยอดเอกสาร 2 ตำแหน่ง [F18] | ไม่สรุปวิธีปัดเศษจากจำนวนตำแหน่งเพียงอย่างเดียว |
| สมุดรายวัน | Draft ยังไม่กระทบงบจนอนุมัติ; Approved มีผลต่อบัญชี [F20] | ต้องแยกผลสำเร็จในการสร้างร่างกับการลงบัญชีแล้ว |

ตัวอย่างตรวจสเปก: ส่งสมุดรายวันเป็นร่างสำเร็จแล้ว ต้องตรวจว่าสถานะยังเป็นร่าง ไม่คาดว่างบเปลี่ยนทันที เอกสาร Journal Entry API รองรับสมุดทั่วไป ซื้อ ขาย จ่าย และรับ [F20]

คู่มือ Document API นิยามฟิลด์ตัวเลขหลายรายการเป็น number; นี่เป็นรูปแบบรับส่งที่ผู้ให้บริการเผยแพร่ ไม่ใช่หลักฐานชนิดข้อมูลจัดเก็บภายใน หรือการอนุญาตให้คำนวณจำนวนเงินด้วย binary floating point ไม่สร้าง schema ทดแทนแล้วอ้างว่าเป็นของผู้ให้บริการ [F18]

### 5.2 PEAK: Authentication, All-in-One และ Queue

ภาพรวม PEAK Open API ระบุ ClientToken, UserToken, Time-Stamp และ Time-Signature ต้องแยกข้อมูลยืนยันสิทธิ์ตามผู้ให้บริการและสภาพแวดล้อม ไม่ใส่ token จริงลงเอกสารวิจัย [P38]

| งาน | Method และ path ที่ตรวจจากเอกสาร | ข้อจำกัดที่ยืนยัน |
|---|---|---|
| สร้างใบแจ้งหนี้ All-in-One | POST /api/v1/Invoices/allinone [P22] | All-in-One 1 เอกสารต่อคำขอ [P21] |
| ส่งสร้างใบแจ้งหนี้ผ่านคิว | POST /api/v1/Invoices/queue [P23] | มี endpoint คิว; ยังไม่รับรองระยะเวลาประมวลผลหรือการส่งซ้ำไม่เกิดเอกสารซ้ำ |
| อ่านผลใบแจ้งหนี้ผ่านคิว | GET /api/v1/Invoices/queue [P24] | ต้องตรวจผลปลายทางจากสัญญา API ก่อนนับว่าสร้างเอกสารสำเร็จ |

ชื่อหน้าของ POST queue ใช้คำ Priority Queue แต่ OpenAPI ในหน้านั้นระบุ path /api/v1/Invoices/queue จึงเก็บ path ตามสัญญาที่อ่าน ไม่อนุมานว่าเท่ากับ endpoint /queue/priority [P23]

ตารางขีดจำกัด PEAK ระบุข้อมูลหลักผู้ติดต่อ/สินค้า/ช่องทางชำระอย่างละ 100 รายการต่อคำขอ, เอกสารทั่วไป 10 ต่อคำขอ, สินค้า 100 บรรทัดต่อเอกสาร, การชำระ 10 รายการและแท็ก 10 ต่อเอกสาร, ใบวางบิล 100 รายการ และสมุดรายวัน 10 ต่อคำขอ ต้องตรวจ endpoint ที่ใช้ประกอบด้วย ไม่เหมารวมว่าแต่ละ endpoint รองรับทุกตัวเลือก [P21]

### 5.3 PEAK: Rate limit และ concurrency

| ขอบเขต | ขีดจำกัดที่เอกสารระบุ |
|---|---|
| POST /api/v1/clienttoken | 10 คำขอต่อนาที |
| GET ต่อ User Token | 20 คำขอที่กำลังประมวลผลพร้อมกัน |
| POST ต่อ User Token | 10 คำขอที่กำลังประมวลผลพร้อมกัน |
| เมื่อเกินขีดจำกัด | HTTP 429; แยก rate จาก concurrency และรอตาม retryAfterSeconds เมื่อมีค่า |

Concurrency เป็นจำนวนคำขอที่ยังไม่เสร็จ ไม่ใช่จำนวนคำขอต่อวินาที ตารางนี้ยกขอบเขตหลัก ไม่แทนข้อยกเว้นราย endpoint ทั้งหน้า [P20]

ตัวอย่างตรวจสเปก: เมื่อรับ 429 ให้เก็บชนิดข้อจำกัดและตรวจเงื่อนไข retry ไม่สรุปว่าใบแจ้งหนี้สร้างสำเร็จหรือยิงซ้ำทันที คู่มือยังไม่ใช่หลักฐานรับประกัน idempotency ของทุกงานเขียน [P20]

### 5.4 PEAK: Webhook

| ApiType | เหตุการณ์ที่คู่มือยืนยัน |
|---|---|
| ApiQuotation, ApiPurchaseOrder | Create, Edit, Void |
| ApiInvoice, ApiExpense | Create, Edit, Void, PaidPayment, VoidPayment |
| ApiReceipt | Create, Edit, Void |
| ApiProduct, ApiService, ApiContact | Create, Edit |

ต้องขอเปิดใช้จากผู้ให้บริการและตั้ง endpoint ตามชนิดข้อมูล รองรับหลาย endpoint และ custom header คู่มือระบุส่งเหตุการณ์จากการทำงานผ่านหน้าโปรแกรมด้วย เมื่อเลือก ApiType ระบบส่งเหตุการณ์ที่รองรับของประเภทนั้น ฝั่งรับจึงต้องแยกเหตุการณ์ที่จะใช้ [P18], [P19]

ตัวอย่างสำคัญ: VoidPayment คือยกเลิกการชำระ ไม่ควรตีความเป็น Void เอกสาร ขณะเดียวกันยังไม่พบหลักฐานเพียงพอในหน้าที่ตรวจเรื่องการเรียงลำดับ, การรับประกันส่งครั้งเดียว, retry schedule และวิธีลงลายเซ็น payload จึงเก็บเป็นรายการตรวจต่อ [P18]

## 7. ควรให้ความสำคัญกับรายละเอียดใดก่อน

รายการต่อไปนี้เป็นข้อเสนอจากการเทียบช่องว่างเอกสาร ไม่ใช่ข้อความรับรองจากผู้ให้บริการ:

1. **ตรวจเอกสารและผลการทำงาน:** OCR ผิดกิจการ, การส่งอนุมัติ, ประวัติส่งอีเมล, ลูกหนี้/เจ้าหนี้ตั้งต้น และความต่างระหว่างร่างกับอนุมัติ ช่วยให้สเปกอธิบายงานจริงได้มากกว่ารายชื่อเมนู
2. **การเชื่อมต่อและข้อจำกัด:** สิทธิ์, ขีดจำกัดคำขอ, Queue, Webhook, การส่งซ้ำ และขอบเขต AI Connector/MCP เพื่อไม่ประเมินความสามารถจากคำว่า “มี API” อย่างเดียว
3. **สินค้าและต้นทุน:** หน่วยแปลง สินค้าไม่นับสต็อก สินค้าชุด และหลักฐาน FIFO; แยกมุมมองต้นทุนเฉลี่ยออกจากวิธีลงบัญชี
4. **งานใช้งานประจำ:** ลิงก์ขอใบกำกับภาษี, วงรอบลูกค้าประจำ, เครื่องพิมพ์หน้าร้าน และการอนุมัติผ่านมือถือ โดยเก็บเงื่อนไขแพ็กเกจรายงานไว้ด้วย
