# ระบบบัญชีแยกประเภท
- ยอดสะสมไม่ต้องเก็บไว้ในฐานข้อมูล ให้ query เอามาจาก ข้อมูลรายวันเลย

## จุดประสงค์และขอบเขต

ระบบสำหรับห้องบัญชีและสำนักงานบัญชี เน้นรับข้อมูล ตรวจสอบ กระทบยอด ปรับปรุงบัญชี ผ่านรายการ และปิดงบ ผู้ทำบัญชีคนเดียวใช้งานได้ตามสิทธิ์ ไม่ต้องติดตั้งระบบอื่นก่อน

รับข้อมูลจากระบบภายนอกหรือนำเอกสารมาคีย์ตรงในรายวันได้ ระบบต้นทางรับผิดชอบ workflow ปฏิบัติงานของตน GL ไม่ทำ POS คำสั่งซื้อ/ขาย ส่งสินค้า คลัง อนุมัติจ่าย หรือสั่งโอนเงิน และไม่มีระบบลูกจ้าง/เงินเดือน

ลูกหนี้ เจ้าหนี้ และธนาคารภายใน GL คือรายละเอียดประกอบบัญชีสำหรับตรวจยอดค้างและจับคู่หลักฐาน การตัดยอดเป็นการบันทึกผลการชำระที่เกิดขึ้นแล้ว ไม่ใช่สั่งรับหรือจ่ายเงินจริง รองรับ many-to-many พร้อมยอดจัดสรร

## ขั้นตอนงานห้องบัญชี

รับข้อมูล/คีย์ใบสำคัญ → ตรวจแหล่งที่มาและรายการซ้ำ → ตรวจเดบิตเครดิต/ลูกหนี้/เจ้าหนี้/ภาษี → จับคู่ Statement → บันทึกข้อแตกต่างและปรับปรุง → ผ่านรายการ → ตรวจรายงานและปิดงวด

Statement จับคู่ภายหลังได้ สถานะตรวจและสถานะผ่านรายการเป็นคนละเรื่อง: ไม่ถือว่า “ผ่านรายการ” เท่ากับ “ตรวจแล้ว” และไม่บังคับผู้ตรวจเป็นคนละคนกับผู้บันทึก

## การคุมเอกสารและงานค้าง

- ตรวจได้ว่าเอกสารรอตรวจ พบข้อแตกต่าง หรือตรวจแล้ว พร้อมผู้ตรวจ เวลา และหมายเหตุ
- เพิ่ม revision ของใบสำคัญทุกครั้งที่เปลี่ยนหัว/บรรทัด/รายละเอียด AR/AP/VAT/WHT ที่กระทบผลตรวจ; ผลตรวจ revision เก่าใช้แทน revision ใหม่ไม่ได้
- เก็บ journal_review_events เป็นประวัติ append-only อ่านสถานะจาก event_no ล่าสุดของ revision ปัจจุบัน ไม่มีผลตรวจให้ถือว่ารอตรวจ
- ยอดค้างรับ/จ่าย ยอดรอจัดสรร และยอด Statement รอจับคู่คำนวณจากข้อมูลจริง ไม่เพิ่มคอลัมน์ยอดสะสม
- การติดตามหลักฐานที่ยังไม่ได้รับเป็นอีกประเด็นที่ยังต้องยืนยันขอบเขต ไม่เหมารวมกับยอดค้างชำระ

## API / MCP และข้อมูลต้นทาง

REST API และ MCP เรียก service บัญชีชุดเดียวกัน ตรวจสิทธิ์และบริษัทก่อนอ่าน/เขียน ไม่เชื่อมฐานข้อมูลโดยตรง และไม่ผ่านรายการอัตโนมัติเพียงเพราะนำเข้าสำเร็จ

ใช้ source_system + source_record_id ต่อบริษัทป้องกันนำเข้าซ้ำ source_type เป็นเพียงประเภทต้นทาง ไม่ใช่ dependency; กรณีแยกเอกสารต้นทางหนึ่งใบเป็นหลายใบสำคัญ ให้ source_record_id เป็น ID รายการย่อยที่คงที่

เมื่อ retry ให้คืนผลเดิมเฉพาะ payload เดิม; payload ต่างต้องเข้ากระบวนการแก้ไขพร้อมตรวจ revision และสิทธิ์ ห้าม overwrite บัญชีที่ผ่านรายการแล้ว ต้องมีรายการกลับ/ปรับปรุงอ้างอิงต้นทาง

## ข้อจำกัดและหลักเทคนิค

ใช้ PostgreSQL เท่านั้น บันทึกผ่าน Go sql.Tx; จำนวนเงินเป็น decimal และ API เป็น decimal string ใช้นโยบายทศนิยมบริษัท ห้าม float ไม่มี MongoDB, ClickHouse, Kafka หรือ Redis

SQL ใน ../../datamodels/gl เป็นร่างสร้างฐานใหม่ ไม่อัปเดตตารางที่มีอยู่ด้วย CREATE IF NOT EXISTS ต้องจัด migration และพัฒนา service/หน้าจอก่อนใช้งานจริง ไม่รวม RD Prep/XBRL รอบนี้


## มิติวิเคราะห์ 6 มิติ (GL Dimensions Parity)

รองรับ 6 มิติวิเคราะห์ตาม Champ 5.5 Pro: แผนก (department), โครงการ (project), การจัดสรร (allocate), งาน (job), หน่วยงาน (part), ฝ่าย (side):
- จอกำหนดรหัสต่างๆ รวม 6 มิติในจอเดียวแบบ Tab/Action พร้อม Master-Detail
- ผังบัญชีกำหนดรหัสที่อนุญาตต่อมิติ: ติ๊กเลือกทั้งหมด (_ALL) = อนุญาตทุกรหัส, ติ๊กเลือกรหัส = อนุญาตเฉพาะรหัสที่เลือก, ติ๊กแต่ไม่เลือกรายการ = ไม่อนุญาตรหัสใด
- สวิตช์ปิด/เปิดมิติระดับบริษัท: มิติที่บริษัทปิดใช้งาน จะไม่แสดงช่องกรอกและไม่ยอมรับรหัสมิตินั้น
- รายงานบัญชีและงบประมาณรองรับตัวกรองและการแยกมิติวิเคราะห์ครบถ้วน
